# 训练配置删除

更新日期：2026-10-29。

## 使用方式与删除范围

在“实验与训练 → 对话训练任务”的配置卡片上，点击“删除配置”，确认后删除。成功后重新查询任务列表；失败时保留卡片，并沿用原有错误提示。

删除的是可重复使用的训练配置。实验、服务器、历史聊天、训练计划、运行、日志、指标和报告都保留，正在运行的训练不会被停止。已删除的任务不能再查询、准备新计划或领取旧计划启动；可以重新创建同名配置。

数据库中的任务行保留删除时间，作为历史计划的关联记录，不会被普通列表和配置查询返回。这是因为已有 chat_training_plans 通过外键引用任务；直接删除行会破坏历史关联。本次不增加回收站、恢复接口或其他任务管理功能。

## 调用流程

```text
TrainingView.vue 点击删除配置
  → confirmAction 显示确认框
  → api.deleteTask(task_id)
  → DELETE /training-tasks/{task_id}
  → require_current_user 校验 Token，取得当前 user_id
  → TrainingTaskService.delete
  → asyncio.to_thread(TrainingRepository.delete_task, user_id, task_id)
  → UPDATE training_tasks SET deleted_at=UTC_TIMESTAMP(6)
       WHERE user_id=当前用户 AND id=目标任务 AND deleted_at IS NULL
  → 提交成功，返回 204 空响应
  → 页面关闭该任务详情并重新查询列表
```

浏览器不能通过请求体指定别人的 user_id。仓储同时匹配任务 ID 和当前用户，更新不到记录时返回 404，避免删除其他人的配置。

## 数据库字段和并发逻辑

- deleted_at：NULL 表示可用；有时间表示已删除。
- active_name：MySQL 生成列。可用任务时等于 name，删除后自动变成 NULL，客户端不负责填写。
- 唯一索引仍叫 uq_training_task_name，但改为 `(user_id, active_name)`。可用任务仍不允许同名；MySQL 唯一索引允许多条 NULL，因此删除后能重新创建同名任务，历史名称保持原样。
- prepare 和 claim 在各自短事务内锁住并检查任务行，与删除的更新互斥；删除前读到的旧对象不能绕过事务内的有效性检查。已经接受并正在执行的启动请求可能与删除并行完成，删除操作不调用 stop，也不撤销已经启动的进程。
- 历史计划和已保存执行快照保留，查看日志、刷新状态等仍使用原有运行链路；服务器配置删除或 SSH 不可用等原有条件仍会影响远端读取。

## 接口契约

```http
DELETE /training-tasks/{task_id}
Authorization: Bearer <当前登录 Token>
```

无请求体；UUID 可使用标准带连字符格式，后端归一为 32 位十六进制字符串。

| 返回 | 含义 |
| --- | --- |
| 204，空正文 | 删除成功，前端不能再调用 response.json() 解析正文 |
| 401 | 未登录或登录失效 |
| 404 | 配置不存在、不属于当前用户或已删除；重复删除也是 404 |
| 422 | 路径 task_id 不是合法 UUID |
| 503 | 暂时失败，页面提示稍后重试；开发者在后端日志定位异常 |

前端开发模式加 `/api` 前缀并由 Vite 转发；后端真实接口不带 `/api`。完整契约同步到 docs/api/openapi.json 与 src/types/api-schema.d.ts。

## 补充：训练指标什么时候采集

后台 Monitor Worker 运行时，在训练进行中持续增量读取日志，默认每约 15 秒检查一次；落后时会更快继续追赶。它从保存的日志 offset 读取新增内容，不是每次从头读。日志中的指标需要符合已有 JSONL 协议，或由配置的指标规则转换。

运行进入 succeeded、failed 或 cancelled 后，还要把最后日志读完，才能生成并确认完整的最终报告。手动“采集指标”也可在训练中执行；只采集一批，不启动训练，也不等于所有历史日志都已经追上。

只启动网页和 FastAPI 不等于启动 Monitor Worker；后台自动采集还依赖监控 Worker 正在运行。训练状态、采集状态和报告状态分别判断。

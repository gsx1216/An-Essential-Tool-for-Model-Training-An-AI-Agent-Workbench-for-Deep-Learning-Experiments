# 论文段落切分、overlap 与完整方法读取

日期：2026-10-28。项目：`E:\code\LangChian_New`。修正原“1,000字符分块、默认读1,000字节”的双重截断；接口数量和三张论文表不变，没有新增依赖或付费调用。

## 为什么调整

问题描述、设计动机、方法步骤和实验条件可能分布在若干段甚至多页。只检索并读到一句匹配文字，不能支持完整模块解释。把存储块调大却仍只给模型1,000字节，也不能解决这一问题。因此本次同时调整切分、正文读取、上下文/证据预算和旧论文重建。

## 当前切分规则

1. pypdf 按物理页提取文字，NFC规范化；保留提取器给出的空行段落，段内换行合并为空格。
2. 该页文字不超过 **6,000字符**时整页保留，避免把本来可一起阅读的问题和方法拆成多个小块。
3. 超长页以 **4,000字符**为目标，优先选择附近完整段落边界，其次句末，最后才按6,000字符硬上限切断。
4. 相邻同页块最多重叠 **600字符**；优先保留末尾完整段落或句子，再退到词边界，无法找到时才按字符。实际重叠量可能小于600，不能再假设固定步长。
5. 块不跨页，保持单块物理页码准确；每块有全篇chunk_index、页码、规范化页内起点和SHA。

例如某页有约5,000字符，包含“问题→动机→方法”，现在是一整块。某页有12,000字符且段落边界出现在3,800、7,600附近，则可在这些边界切开，再按末尾段落/句子选择重叠；具体位置以提取文字为准，不固定从某个序号重新开始。

6,000个英文字符包含字母、空格和标点，通常能容纳数百至约千个词，不等于6,000个单词或token。保持段落有助于阅读，但没有使用大模型判断语义边界，也没有保证自动识别完整章节。PDF没有可靠空行、多栏顺序异常或公式提取不完整时，切分也不能还原视觉结构。

## 模型怎样读完整方法

```text
关键词检索命中块
    ↓
读取正文：默认12,000 UTF-8字节，上限18,000
    ↓
next_offset 非空 → 继续读取当前块
    ↓
问题、动机、实现是否完整？
    ├─ 不完整 → 根据前后块序号读取同一论文相邻块/页
    └─ 已有足够证据 → 形成解释，并引用实际片段
```

read_paper_chunk新增返回 `previous_chunk_index`，继续保留 `next_chunk_index`。工具可以使用 `paper_id + chunk_index` 读相邻块，不需要另建会话或猜UUID；HTTP客户端仍通过 `/{paper_id}/chunks` 找到对应块ID再读取。next_offset是字符位置，max_bytes是UTF-8字节，二者不能混算。

聊天和建议Agent规则明确要求：询问模块、问题、动机和方法时先完整读命中块，按需读前后块；不能用一句话冒充整个模块。它仍是模型按需决定继续阅读，不是服务器自动识别并读取整章。聊天每轮现有6次、建议现有8次工具调用上限不变；超出预算应说明缺失部分，可继续提问，不声称完整阅读。

## 为什么还要调整数据库和预算

原聊天工具证据只有4 KiB上限，正文增大后会在保存审计时失败。本次将论文读取的应用审计上限及数据库CHECK增量扩到24 KiB；其他工具仍按原4 KiB校验。论文单结果允许最多20,000字节，论文模式总结果最多输入预算的三分之二且不超过32 KiB，同时还受当前剩余输入约束；普通模式预算不变。

独立建议的PDF正文证据允许最多6,000字符，单次实际工具结果仍不超过其原有16 KiB持久化上限。中文很长时可能需要用next_offset继续读；不会为了宣称完整而越过真实输入预算。

MySQL仅改变两条CHECK：paper_chunks正文从1,000到6,000字符、chat_tool_calls元数据从4到24 KiB。不新增表，不清空数据、不修改全局MySQL参数。执行 `python -m app.database --paper-schema` 可重复完成升级。

## 已上传论文如何生效

重启API和建议Worker后，新上传使用 `pypdf-版本/paragraph-v2`。旧论文不自动重建，避免不经操作就让现有块ID全部变化。

在Swagger调用：

```http
POST /papers/<本人真实paper_id>/retry?rebuild=true
Authorization: Bearer <access_token>
```

没有请求正文。保留原始PDF，重新解析并生成新分块。默认 `rebuild=false` 保持ready论文直接返回旧结果的行为；只有显式true才重建。

重建领取现有处理租约，活跃处理返回409；新分块和旧分块替换在同一事务，写入失败回滚，不留下半份索引。重建期间论文为processing，不提供旧版索引检索；失败或失联仍通过原重试流程恢复。成功后旧chunk_id新读取返回404，但之前聊天/建议保存的实际引文快照不变，原件SHA不变。

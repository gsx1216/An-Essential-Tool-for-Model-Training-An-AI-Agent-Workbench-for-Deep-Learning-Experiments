# 可恢复对话：先保存问题，再生成回复

本次已完成数据库、仓储、ChatService 的发送与重试逻辑以及测试。命令行尚未接入模型调用与“继续”操作，这是下一步由你手写的部分。

## 四张表的职责

| 表 | 保存的内容 |
| --- | --- |
| users | 应用用户 |
| chat_sessions | 用户拥有的聊天会话、标题 |
| chat_messages | 实际消息正文和会话内 seq；未回复的问题也在这里 |
| chat_turns | 一轮问题的状态、对应的用户消息序号、本次生成任务编号与有效期 |

一次提问对应一个 turn_id。一次生成尝试对应一个 attempt_id。失败后重试沿用 turn_id，重新生成 attempt_id。

| status | 含义 | 接下来可以做什么 |
| --- | --- | --- |
| pending | 问题已提交，尚未开始生成 | 领取并生成 |
| running | 已有生成任务在处理 | 等待；任务过期后可以重新领取 |
| failed | 上一次生成失败，问题仍在 | 重新领取并生成 |
| completed | 回复已保存 | 开始下一轮 |

第一版同一会话最多有一个未完成轮次。这个规则同时由短事务中的会话锁、数据库唯一索引保证。不会在等待模型回复期间持有数据库锁。

## 仓储方法

以下方法都校验用户 ID、UUID 和会话归属。数据库方法是同步的，在异步服务里通过 await asyncio.to_thread(...) 调用。

### start_turn(user_id, session_id, content, request_id=None) -> str

在同一个事务中保存用户提问、pending 轮次及会话更新时间，返回 turn_id。即使后面的模型调用失败，这里的提交也不会被撤销。

序号由仓储从数据库当前最后一条消息计算，不再让 ChatService 用 len(history) 计算。不需要调用者传 start_seq。

request_id 不传时由后端生成 UUID。正式接口中，一次发送的网络重试应复用同一个 request_id：同一个 ID 和相同问题返回原 turn_id，不重复插入；相同 ID 不允许改成另一道问题。

### claim_turn(user_id, session_id, turn_id, lease_seconds=600) -> (attempt_id, messages)

领取生成任务，返回本次 attempt_id 和完整历史。**返回的 messages 已经包含本轮问题，不要再追加一次。**

pending、failed、过期的 running 可以领取；仍在有效期内的 running 会拒绝重复领取；completed 不重复生成。领取只读写数据库，事务完成后才去请求模型。

默认生成任务有效期为 600 秒，可以指定 1～3600 秒。意外退出而没有标记失败的任务，需要等有效期结束后重新领取。目前没有自动心跳续期或后台自动重试；未来长时间任务要另加续期机制。

### complete_turn(user_id, session_id, turn_id, attempt_id, assistant_content) -> None

只插入模型回复，并把轮次改为 completed，在一个事务中提交。写入出错则撤销本次回复与状态变化，原先已提交的用户提问仍保留。

同一 attempt_id 和相同回复重复提交不会重复插入。旧任务、过期任务、不同内容的重复完成都会被拒绝。

### fail_turn(user_id, session_id, turn_id, attempt_id, error_code="MODEL_REQUEST_FAILED") -> None

只标记 failed，不删除问题，也不插入假回复。错误字段只记录简短错误代码，不要传入包含密钥、请求正文等信息的原始异常。旧 attempt_id 不能覆盖新任务或已完成状态。

### get_unfinished_turn(user_id, session_id) -> ChatTurn | None

找出未完成的一轮，返回对象中的 turn_id、status 等字段；没有时返回 None。界面以后可以用它显示“等待回复、重试”等状态。

### load_messages(user_id, session_id) -> list[tuple[str, str]]

保持原接口，读取所有已保存的消息，包括还没有模型回复的问题。

## 已完成的 ChatService

三个异步入口/步骤已经实现：

1. send_message：校验输入 → start_turn 保存问题 → 等待 _generate_reply。
2. retry_message：查询未完成轮次 → 等待 _generate_reply；不要重复保存原问题或“继续”两个字。
3. _generate_reply：claim_turn → 组装模型请求 → await 模型 → complete_turn → 返回回复。

已有的消息组装代码移到了 _build_model_messages。这里不再追加 content，因为问题已经由 start_turn 保存，claim_turn 的 messages 里已经有它。

模型调用和回复校验放在一个 try/except 中：失败则 fail_turn，再重新抛出原异常。complete_turn 放在该 try/except 之外，数据库写回失败不应被当成模型失败，也不要因此立即再次调用模型。

如果回复已生成但写回失败，可以在任务仍有效时重试同一次 complete_turn。若程序彻底退出，旧结果没有持久化，则等待任务过期后重新生成。

命令行以后需要明确把“有未完成问题时的继续”路由到 retry_message。大模型不会自动恢复上次进程，它只是根据已有历史重新生成。目前这段界面路由尚未实现。

同一个请求 ID 已经完成时，ChatService 通过 get_completed_reply 读取原回复，不会再次请求模型。模型等待被取消时会尝试记录 MODEL_REQUEST_CANCELLED；如果进程被强制终止而无法记录，仍可通过任务过期重新领取。

## 你下一步的手写任务

在 chat_cli.py 中保留已有的会话选择，接着完成：

1. 加载模型 API Key，创建 ModelGateway、MessageRepository、ChatService。
2. 用 while 循环读取用户输入；空输入跳过，exit 退出。
3. 普通提问等待 service.send_message(user_id, session_id, text)。
4. 输入“继续”或“重试”时，先检查有无未完成轮次：有则等待 service.retry_message；没有则可把“继续”作为普通新提问。
5. 调用成功后打印回复；失败时提示本轮未完成，可以重试。数据库连接错误也要明确提示，不要一律承诺已经保存成功。

CLI 不再自行追加消息、计算 seq 或调用 start_turn/complete_turn；这些由服务和仓储完成。进入旧会话时，即使历史最后只有 human 消息，也能正常显示它。

```powershell
python -m unittest discover -s tests
```

真实 MySQL 集成验证使用配置中的连接，在单独创建的随机临时数据库测试，结束后只删除该临时库：

```powershell
python -m scripts.verify_turns_mysql
```

它覆盖问题先落库、失败保留、重试不重复、并发只能一个领取成功、旧任务写回拒绝、回复事务回滚、重复初始化及旧单条问题兼容。

开发用手动演示会在业务库新建一个“可恢复消息测试”会话并留下测试消息，不调用真实模型：

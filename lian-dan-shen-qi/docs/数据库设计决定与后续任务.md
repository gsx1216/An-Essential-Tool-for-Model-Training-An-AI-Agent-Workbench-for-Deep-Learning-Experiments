# 数据库设计决定与后续任务

记录日期：2026-10-25

## 一、这次确定的设计

继续使用共享业务表，不按用户名或用户 ID 动态创建表。

| 表 | 职责 |
| --- | --- |
| chat_sessions | 保存会话及所属 user_id、标题和时间 |
| chat_messages | 保存 session_id、seq、role、content 等原始消息 |
| chat_context_summaries | 每个会话保存一份当前摘要、覆盖序号、版本和缺口信息 |

一个用户可以拥有多个会话，一个会话可以拥有多条消息。查询消息时，通过 chat_messages.session_id = chat_sessions.id 联表，再用当前登录用户的 user_id 校验归属。后端从登录凭证确定用户，不能相信请求自行声明的用户身份。

联表查询与联合索引不是一回事。现有消息表的 (session_id, seq) 唯一索引同时约束消息序号；是否使用索引及具体效率，需要用 EXPLAIN 和实际数据验证。

共享表不代表每次都把全表取出：界面历史分页读取；模型上下文读取摘要以及摘要未覆盖的原文。上下文摘要不会自动删除原始消息，也不等于减少 MySQL 的原文存储量。

将来接入 Redis 时，MySQL 继续作为持久化记录来源。Redis 可以用于热数据缓存或任务通信，需要配套失效和恢复机制，不能仅靠缓存解决长期容量问题。

## 三、已完成：数据库容量检查与查询验证

先做一个由服务器维护者运行的只读检查脚本，不增加面向普通用户的数据库管理接口。

已实现的检查范围：

1. 业务表的数据空间、索引空间以及估计行数。明确 InnoDB 元数据中的行数是估计值，容量也不是精确的磁盘剩余量。
2. 指定会话的消息条数、正文大小及摘要覆盖位置；单会话统计应有明确的查询范围。
3. 历史分页、摘要后历史读取的 EXPLAIN 结果，核对现有索引与查询条件。
4. 输出可读报告，帮助决定是否需要后续优化。

安全与验收要求：

- 不输出正文、模型 Key、Token、数据库密码或其他用户敏感内容。
- 不清空表、不修改线上记录、不自动归档或删除历史。
- 不默认对全部生产消息执行高成本精确统计。
- 有意义的性能验证使用独立临时数据库与模拟数据；只有显式运行时才生成测试数据，完成后仅清理本次创建的临时库。
- 报告区分估计值、实际统计和查询计划；不凭行数直接声称系统能支持多少用户。
- 生成配套 Markdown，解释脚本、SQL、调用方式、结果含义及验证记录。

2026-10-25 已完成只读脚本、配套文档、19 项专项测试和 9 组真实 MySQL 临时库验收；完整常规回归 693 项通过。启用计时后额外创建 12,000 条模拟消息，两条历史查询均选择现有联合索引；这只是本机小规模顺序查询，不是生产并发容量承诺。临时库已清理，没有调用收费模型。

入口：python -m scripts.check_database_capacity。详细说明见 [数据库容量检查与查询验证说明](数据库容量检查与查询验证说明.md)。

## 四、完成检查后回到实验功能主线

1. 实验记录管理（已完成）：experiments 表及创建、分页列表、详情接口；所有操作校验当前用户归属。先登记实验，不接受任意系统命令执行。
2. 实验运行记录（基础已完成）：experiment_runs、定义和参数快照、幂等创建、状态元数据与结果/日志引用预留；真实状态由下一阶段执行器驱动。
3. 执行目标与独立执行器：服务器配置、执行绑定、已登记脚本启动、stdout/stderr、状态及停止已完成本地验证；接着补真实 Linux 验收、后台同步和异常接管；耗时任务不绑在一次 HTTP 请求里。
4. 指标与监控：结构化 JSONL 指标采集、质量标记和事实报告基础已完成；自动后台采集、监控触发和长日志独立指标通道仍待补充。
5. 分析与建议 Agent：读取运行证据和有界日志，联网检索相关研究和官方资料，给出带可核查来源及验证方案的建议；接入全新会话结果问答。
6. 变更追踪与任务通信：保存实际 diff 与关联运行结果，再接入 Redis Streams，补齐幂等、重试、租约和恢复机制。

各阶段分别完成代码、正常与失败路径验证、模块说明文档。模型验证优先使用模拟对象，不自动产生付费调用。

## 五、容量持续增长时的处理顺序

先观测查询耗时、数据库空间和增长速度，再根据实际需求决定历史保留及归档策略。任何自动清理策略都须先明确用户是否允许删除以及如何恢复。

训练完整日志、模型权重和大型产物优先放文件或对象存储，数据库保存引用及必要元数据。只有测量表明单库或单表达到瓶颈时，才评估固定分片或其他扩展方案，不以每人一张表作为默认方案。

早期《实验自动运行与多Agent监控系统设计方案.md》曾推荐 PostgreSQL；当前实际项目已采用 MySQL，本计划按现有 MySQL 实现继续推进，不要求换库。

# 数据库容量检查与查询验证说明

日期：2026-10-25。项目：E:\code\LangChian_New。

指标和事实报告接入后，检查范围已增加到十四张（包含 experiments、experiment_runs、server_connections、run_executions、run_metric_streams、run_metric_events、run_reports），临时库验收同步更新。原阶段的计时和报告是历史样本；当前完整回归为 893 项，本阶段容量临时库 8 组验收通过。详见 [服务器连接配置与SSH工具基础说明](服务器连接配置与SSH工具基础说明.md)。

## 1. 本阶段解决什么问题

多个用户共用 chat_sessions 和 chat_messages，需要知道数据增长了多少、历史查询是否按预期走索引。本次增加维护者命令行诊断工具，不改变聊天表设计，不新增普通用户 HTTP 管理接口。

现在可以查看十四张业务表的空间估计、估计行数和索引定义；指定用户与会话后，还能精确统计有限范围内的消息数量、正文 UTF-8 字节数、摘要覆盖点，并查看两条实际历史 SQL 的查询计划。

输出同时显示在终端并保存为 Markdown。默认只检查元数据，不扫描全部消息正文，不运行模型。

## 2. 从哪里开始运行

先激活已有 langchain 环境，在项目根目录运行。沿用服务器环境变量或 config/.env 中的 MYSQL_PASSWORD，命令不要求输入密码，也不接收命令行密码参数。

```powershell
Set-Location E:\code\LangChian_New
python -m scripts.check_database_capacity
```

执行后终端会打印报告，并显示保存位置。默认位于 data/diagnostics/database_capacity_时间_随机后缀.md，每次创建新文件。

仅指定输出路径：

```powershell
python -m scripts.check_database_capacity --output data/diagnostics/my_capacity_report.md
```

已经存在的文件不会被覆盖，返回退出码 1；需要换一个文件名。

想查看某个会话时，同时指定其真实用户 ID 和完整会话 UUID。下面的占位文字需要替换，不能照抄为 UUID：

```powershell
python -m scripts.check_database_capacity --user-id 1 --session-id "替换为该用户的真实会话UUID" --sample-limit 100
```

这是服务器维护工具，user-id 是维护者选择检查范围，不是登录方式。普通用户仍需通过 HTTP Token 确定身份。脚本还会联表核对会话归属，错误归属和不存在会话均拒绝检查。

继续检查较后的范围时，提供上次报告的 last_seq：

```powershell
python -m scripts.check_database_capacity --user-id 1 --session-id "替换为该用户的真实会话UUID" --after-seq 100 --sample-limit 100
```

不要将“统计了 100 条”直接当作“last_seq 一定为 100”，历史可能存在序号缺口。

所有参数说明：

```powershell
python -m scripts.check_database_capacity --help
```

| 参数 | 默认 | 约束和作用 |
| --- | --- | --- |
| --user-id / --session-id | 不提供 | 必须成对提供；检查已有会话，不创建用户或会话 |
| --after-seq | 0 | 0～BIGINT UNSIGNED 最大值，只统计此序号之后的消息 |
| --sample-limit | 1000 | 1～10000，单次统计的消息数量上限 |
| --page-size | 50 | 1～100，仅用于界面历史 SQL 的 EXPLAIN 参数 |
| --max-execution-ms | 2000 | 100～30000，每条普通只读 SELECT 的服务端时间限制 |
| --output | 自动生成 | 新报告路径，使用独占创建模式，拒绝覆盖 |

## 3. 调用顺序与每一步校验

```text
scripts.check_database_capacity.main
  → argparse 解析参数，要求 user-id 和 session-id 同时出现
  → get_mysql_password 读取服务器配置
  → CapacityRepository 构造并加载固定 SQL；此时不连接数据库
  → inspect 校验用户 ID、UUID、序号与各项上限
  → get_connection 建立本次专用连接
  → 设置本连接 SELECT 超时和元数据锁等待时间
  → 开启 REPEATABLE READ + 一致快照 + READ ONLY 事务
  → 查询固定十四张表的元数据和索引
  → 若指定会话：核对归属 → 读摘要序号和版本 → 有限消息统计
                → 查询是否还有后续消息 → 普通 EXPLAIN 两条业务 SQL
  → finally rollback 结束读取事务，并关闭连接
  → render_capacity_report 生成 Markdown
  → 独占新建报告文件，再向终端显示报告
```

这里使用 rollback 只是结束只读快照，并不是“先修改再撤销”。脚本根本没有业务写入 SQL，也不调用初始化建表函数。诊断耗时单独记录，不能当成聊天接口耗时。

没有使用 async/await：这是维护者手动运行的同步命令，不占用 FastAPI 请求的事件循环，不需要为了形式再套异步。

## 4. 新增 Python 模块与引用的包

### app/repositories/capacity_repository.py

负责数据库读取，入口为 CapacityRepository.inspect。构造器只读 SQL；inspect 负责范围校验、短只读事务、汇总安全结果。

- app.database.get_connection：复用现有 MySQL 连接入口。当前仍连接本机 127.0.0.1:3306，不改变服务连接配置。
- app.validators：复用正整数、BIGINT 范围及 UUID 校验。bool 不会被当成合法整数。
- SessionNotFoundError：表达会话不存在或归属不符，避免继续读取消息统计。
- logged_operation：记录安全的操作结果、耗时和错误位置，不记录密码、参数、结果或正文。
- pathlib.Path：从项目 sql 目录加载文件。
- datetime / timezone：报告使用明确的 UTC 时间。
- time.perf_counter：测量本次检查的单调时间，不用系统时钟差值。
- re：库名白名单和报告标识符校验。库名只允许固定项目库或内部生成的临时验收库，CLI 不提供任意库名/任意 SQL 输入。

safe_plan 只投影表别名、访问方式、索引名称、估计行数及 filesort/temporary 布尔标志。原始 EXPLAIN 中的 ref、完整 Extra 等字段不直接写入报告，避免把常量值或不必要的信息带出来。

### app/services/database_capacity_service.py

负责 render_capacity_report 和字节显示。输入为仓储已经筛选的诊断结果，输出 Markdown 字符串，不连接数据库，也不持有密码。

报告会提示表不可见/缺失、预期联合索引未找到、统计窗口后仍有消息等情况。它不会自动建索引、分表、删历史或断言服务器已经具备某种容量。

### scripts/check_database_capacity.py

负责命令行参数、调用仓储、保存报告、处理可预期错误。

- argparse：生成 --help、解析开关；缺少配对参数时返回退出码 2。
- pathlib.Path：定位输出文件，必要时建立报告父目录。
- uuid.uuid4：报告自动命名的随机后缀，降低重名概率。
- mysql.connector.Error：识别数据库异常；普通数据库失败不向终端输出原始错误文本，超时 3024 给出缩小范围提示。
- get_mysql_password：沿用服务器配置，优先使用已有环境变量，本地配置由现有 python-dotenv 加载。
- logging / configure_logging / log_failure：把失败写入项目安全日志，保留源码位置、异常类型和 MySQL 错误编号。
- sys：输出安全错误到 stderr，并返回退出码。
- datetime / timezone：生成 UTC 文件名。

成功退出码为 0；业务参数、配置、数据库和文件错误为 1。原始密码、用户名、会话 UUID 和正文不会写入报告；会话 UUID 本身仍可出现在维护者自己的命令历史中。

### scripts/verify_database_capacity_mysql.py

独立临时 MySQL 验收工具。随机创建 `_codex_capacity_` 加 32 位十六进制的库，复用项目 DDL，并写入模拟用户、会话和消息。所有临时建表、插入、测试 SELECT 和清理仅针对这个内部生成的名称。

finally 中再次校验库名才执行 DROP DATABASE。CLI 不接受目标库名，不能拿它清理项目库。运行进程被强制杀死、机器断电或 MySQL 无法连接时，finally 可能无法完成，需要维护者按日志检查本次临时库；脚本没有扩大范围清理的逻辑。

--benchmark 才额外创建多会话数据并执行顺序查询计时。使用 statistics.median 算中位数，math.ceil 取最近秩 P95；perf_counter 计时，字节及条数在本机读取核对。查询返回的模拟正文不会打印或写入报告。

### tests/test_database_capacity.py

使用 unittest、unittest.mock、临时目录和内存 stdout/stderr 验证：不连接真实数据库的默认行为、非法输入提前拒绝、归属校验、只读事务、异常回滚、范围限制、计划脱敏、CLI 新文件保护和临时库名称保护。常规测试不生成付费模型请求。

## 5. SQL 文件分别负责什么

| 文件 | 职责 |
| --- | --- |
| sql/capacity_tables.sql | 在 information_schema.TABLES 中按固定库和十四张预期表读取估计行数与空间 |
| sql/capacity_indexes.sql | 按列顺序读取索引名称、唯一性、列名和可见性 |
| sql/capacity_owned_session.sql | 同时按 user_id 和会话 ID 核对归属，不读取标题或用户名 |
| sql/capacity_summary_state.sql | 只读摘要覆盖序号和版本，不读取摘要正文 |
| sql/capacity_message_sample.sql | 对有 LIMIT 的会话消息窗口聚合 COUNT、正文字节数和首尾序号 |
| sql/capacity_has_more.sql | 只找统计末尾之后的下一条 seq，区分完整后缀与截断窗口 |
| sql/load_history_page.sql（复用） | 原界面分页 SQL；前加普通 EXPLAIN 检查查询计划 |
| sql/load_context_messages.sql（复用） | 原摘要覆盖点之后的历史 SQL；前加普通 EXPLAIN 检查计划 |

变量值通过 cursor.execute(sql, parameters) 参数化传入，不拼接用户 ID、会话 ID 或正文。只有受严格白名单限制的内部库名用于验收库替换。

有限统计中的 content_bytes 使用 OCTET_LENGTH，表示 UTF-8 正文字节，不是模型 token、不包括行头和索引。SUM 对空范围转换为 0；序号缺口按真实消息统计，不用 last_seq-first_seq 估算条数。

## 6. 报告如何解读

估计行数来自 TABLE_ROWS，不能据此断定消息的精确总条数。InnoDB 的 DATA_LENGTH 是聚簇索引分配空间估计，INDEX_LENGTH 是非聚簇索引分配空间估计，可能缓存或滞后。[MySQL TABLES 文档](https://dev.mysql.com/doc/refman/8.0/en/information-schema-tables-table.html)

计划里的 key 表示本次优化器选择的索引；rows 是优化器估计。普通 EXPLAIN 说明计划；EXPLAIN ANALYZE 会真正执行查询，本脚本不使用后者。看见 ALL 或 filesort 不能单独断定设计错误，应结合过滤范围、表规模和真实测量判断。[MySQL EXPLAIN 文档](https://dev.mysql.com/doc/refman/8.0/en/explain.html)

SELECT 时间限制是本连接、每条语句的限制，不是脚本整体硬期限，也不能承诺覆盖所有驱动网络等待。另设置本连接 lock_wait_timeout=3，限制元数据锁等待；不修改全局配置。[MySQL max_execution_time 文档](https://dev.mysql.com/doc/refman/8.0/en/server-system-variables.html#sysvar_max_execution_time)

报告按受检会话的真实 seq 读取同一只读快照；元数据估计不属于精确业务计数，也不是整个服务的实时原子容量快照。只有起点为 0 且 has_more 为否时，消息统计才覆盖本会话当时的全部现存消息。

这不是自动容量监控或告警服务；没有启动定时任务、后台轮询、归档或自动清理。重复运行并保留报告可以人工观察趋势，后续需要时再增加指标采集。

## 7. 验证命令与本次结果

常规单元测试，不需要真实 MySQL：

```powershell
python -m unittest tests.test_database_capacity -v
python -m unittest discover -s tests
```

真实 MySQL 临时库验收：

```powershell
python -m scripts.verify_database_capacity_mysql
```

显式启用小规模查询计时，默认增加 24 个会话 × 500 条，共 12,000 条模拟消息：

```powershell
python -m scripts.verify_database_capacity_mysql --benchmark
```

可选 --sessions、--messages-per-session、--repetitions；范围分别为 2～100、2～2000、1～50，数据总量不超过十万条。默认计时每条查询预热一次后测量五次。每次验收在 data/diagnostics 的随机子目录保存样例报告；启用计时再保存 benchmark_report.md。

2026-10-25 本次验证记录：

- 专项 19 项、完整常规回归 693 项通过。
- 本机 MySQL 8.0.46，启用计时的 9 组验收通过；临时库已清理。
- 空会话、无摘要、seq 缺口、范围截断、错误用户、丢失会话都已覆盖。
- 服务端 READ ONLY 事务确实拒绝 INSERT；超时探针确实被中断。
- SLEEP 独立查询被超时中断时可能返回 1，不抛异常；验收兼容这种服务器行为。普通业务 SELECT 的 3024 异常另有单元测试。[MySQL SLEEP 文档](https://dev.mysql.com/doc/refman/8.0/en/miscellaneous-functions.html#function_sleep)
- 默认维护 CLI 还读取了现有项目库的元数据，七张表均可见，预期联合索引存在；没有读取实际会话正文、修改业务记录或执行迁移。

上述耗时仅是本机、小规模、单连接、预热后的样本。没有做真实多用户并发压测，也不能推出千万消息下的性能。没有调用收费模型，没有安装新包。

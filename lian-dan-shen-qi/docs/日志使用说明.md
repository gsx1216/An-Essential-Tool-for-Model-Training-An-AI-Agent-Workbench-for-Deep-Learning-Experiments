# 日志使用说明

`raise` 负责把异常交给调用者，不负责把异常保存成日志。本项目用 Python 标准库 `logging` 将重要操作和异常持久化。

## 去哪里看

默认目录为项目根目录的 `logs/`，文件按 UTC 日期和进程编号分别保存，例如：

```text
logs/
  2026-10-21/
    app-12345.log
    app-12345.log.1
```

默认使用便于阅读的文本格式，参考用户提供的“马来西亚舆情预警系统”中 `event_sphere_malai/utils/about_log.py` 的布局。控制台和文件均显示时间、级别、模块、函数、行号、线程、请求编号和操作结果；异常另列原因分类和调用栈。每个进程的单文件上限为 5 MiB，保留当前文件和 3 份轮转备份。默认保留最近 7 个 UTC 日期的日志；首次写入和日期切换时清理过期日志。被占用而不能删除的旧文件留待下次清理。日志目录已加入 `.gitignore`。

下面是格式示意，行号和请求编号以实际运行结果为准：

```text
2026-10-22 08:00:00.123456 UTC | ERROR    | app.repositories.login_session_repository:save_session:75 [app/repositories/login_session_repository.py] | asyncio_0 | request_id=0123456789abcdef0123456789abcdef | 执行失败 operation=login_session_repository.save_session error_type=ProgrammingError errno=1146
  原因：数据库表不存在
  异常链[1]：ProgrammingError errno=1146
    app/repositories/login_session_repository.py:75 in app.repositories.login_session_repository.save_session
    cursor.py:416 in mysql.connector.cursor.execute
```

成功日志的位置指向被装饰的业务函数定义；失败日志优先指向根因中最深的业务代码行，而不是日志包装函数。下面的安全调用栈保留其他调用位置，便于继续追查第三方库错误。项目内路径从项目根目录起算，便于区分不同目录中的同名文件。

不同进程使用不同文件，避免多个 Uvicorn worker 同时轮转同一个文件。日期到来时，新事件写入当天文件。

服务端环境变量可调整行为，无需新增接口：

- `APP_LOG_DIR`：日志目录；默认项目根目录下的 `logs`。
- `APP_LOG_LEVEL`：`DEBUG`、`INFO`、`WARNING` 或 `ERROR`，默认 `INFO`。
- `APP_LOG_FORMAT`：默认 `text`；设为 `json` 时恢复每行一个 JSON 对象的结构化输出，便于日志采集程序处理。切换后重启后端；已生成的文件不会改写。
- `APP_LOG_CONSOLE=0`：只写日志文件，关闭应用日志的控制台副本。文件输出失败时仍会给控制台固定告警。

本模块直接读取进程环境变量，不会为读取日志配置而加载包含密码的 `.env`。

## 如何找到一次错误

接口响应头中的 `X-Request-ID` 是服务端生成的请求编号。它只是排查编号，不是登录凭证。客户端传入的同名头不会被信任。

复制响应头中的编号，在整个 `logs/` 目录中搜索，可以看到同一次请求经过的操作和最终结果。异步调用以及 `asyncio.to_thread` 中的数据库操作保留相同编号。

日志中的常用字段：

| 字段 | 含义 |
|---|---|
| `time` | UTC 时间 |
| `event` | 事件，例如 `operation_succeeded`、`operation_failed`、`request_completed` |
| `operation` | 操作名称，例如 `login_session_repository.save_session` |
| `request_id` | 本次请求或独立操作的排查编号 |
| `status_code` | HTTP 响应状态码 |
| `duration_ms` | 耗时，单位为毫秒 |
| `source` | JSON 中的模块、项目内文件路径、函数和行号；文本日志直接显示这些位置 |
| `thread_name` | 执行线程名；文本中也直接显示，例如 `MainThread`、`asyncio_0` |
| `error_type`、`errno`、`reason` | 异常类型、数据库错误编号和固定原因分类 |
| `exceptions` | 异常类型、MySQL 错误编号、文件名、函数名和代码行号 |

## 哪一层负责记录

已实现的仓储和业务服务入口使用 `@logged_operation(...)` 统一记录结果，包含用户、聊天会话、消息轮次、登录记录、模型调用以及旧本地历史存储。装饰器不记录参数或返回值，不改变原函数的调用方式。

数据库方法仍负责 `commit()`、`rollback()` 和 `raise`；日志不能代替事务处理。保存登录记录时，回滚之后必须 `raise`，否则上层可能误以为保存成功。

HTTP 中间件记录路由模板、状态和耗时；认证路由记录已处理的失败；未处理异常由中间件记录并返回 HTTP 500 和 `{"detail":"请稍后重试。"}`。数据库异常仍返回 HTTP 503 和同样的通用提示。

同一次请求内，同一个异常及其原因链的详细日志去重；仍会另有一条 HTTP 请求结果日志。这两条分别回答“哪里失败”和“请求最终怎样结束”。

用户名已存在、密码错误、输入校验等预期拒绝记录为 `WARNING`，不把它们当成后台故障。后台异常记录为 `ERROR`。422 请求校验失败只记录安全的请求结果。`DEBUG` 额外记录业务入口开始执行的事件。

原始 Uvicorn 访问日志由本中间件的请求日志替代，避免额外打印原始 URL 查询参数。第三方模型库不启用 DEBUG，模型请求使用现有用户凭据；本次日志测试不调用收费模型。

## 敏感信息处理

不记录密码、密码哈希、API Key、原始 Token、Token 哈希、SQL 参数、请求/响应正文、请求头、Cookie、查询参数或局部变量。日志只接收少量允许的技术字段。

异常的原始文本也不直接保存：数据库重复键等异常文本可能包含数据值。排查时使用异常类型、MySQL `errno`、原因链和文件行号，不把原始异常字符串拼接进日志。

可读原因由固定分类生成，例如 1146 对应“数据库表不存在”、2003 对应“无法连接数据库服务”，不会输出异常中可能携带的 SQL 参数。参考项目的 Loguru `diagnose=True` 会展示局部变量，本项目继续使用标准库日志和安全堆栈，不开启局部变量转储，也无需安装额外日志包。

`logger.exception("operation_failed")` 可以记录安全堆栈。格式化器不会输出源码行、局部变量或原始异常文本。不要添加 `logger.error(str(error))`、打印整份请求或临时打开第三方库的请求正文调试。

日志文件由后端维护，不提供给普通用户下载，也不放进静态资源目录。上线时需限制日志目录的读取权限。

## 验证

```powershell
python -m unittest discover -s tests
python -m scripts.verify_login_sessions_mysql
python -m scripts.verify_user_passwords_mysql
python -m scripts.verify_readable_logging_mysql
python -m scripts.verify_current_user_api_mysql
```

单元测试包括日志落盘、轮转、旧日志清理、并发请求编号、线程中的编号传递、错误去重、敏感信息隔离、预期拒绝、未处理 500、已处理 503、依赖失败和磁盘输出失败。

这些 MySQL 验证脚本使用独立临时库，测试后仅清理本次临时库。`verify_readable_logging_mysql` 使用真实本机 MySQL 验证“登录记录表缺失 → HTTP 503 → 可读日志显示 1146、业务文件和行号”，再创建临时表验证正常登录；它不调用模型，也不写业务库。`verify_current_user_api_mysql` 覆盖客户端提交 Token 后的身份校验和错误日志；退出登录业务与 HTTP 接口仍是下一阶段练习。

参考：[Python logging](https://docs.python.org/3.12/library/logging.html)、[OWASP 日志中的敏感数据处理](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html#data-to-exclude)。

## 1. 现在怎样处理

```text
prepare(history, summary)
    ↓ 校验消息对象、角色、序号和旧摘要
计算系统提示词 + 当前问题
    ├─ 未超限：继续原来的短输入 / 旧历史摘要流程
    └─ 超限：await _prepare_long_input(history, summary)
                 ↓ 保留原文，创建 working_history 副本
                 ↓ 计算历史、旧摘要、缺口标记的占用，给当前问题分配精简目标
                 ↓ await input_compressor.compress(原文, target_tokens=目标)
                        ├─ 完整精简请求放不下：先切块，每块都提取问题和必要材料
                        └─ 中间结果仍过长：有限次数合并精简
                 ↓ 将精简稿放到本次副本，原来的 seq、role 不变
                 ↓ 对系统提示词 + 旧摘要 + 历史 + 缺口标记 + 精简稿完整重计数
                      ├─ 不超过硬预算：返回 PreparedContext
                      └─ 仍超限：提示拆分任务，原文保持不变
```

系统提示词不会被精简。模型只负责提取当前输入中的目标、必要材料和限制，不在精简阶段回答用户的问题；真正回答要由后续调用方使用 result.model_messages 发起。

如果旧历史很长，会按计划保留的近期原文和摘要额度给问题精简预留空间；问题精简后完整上下文仍超限时，继续进入旧历史摘要分支。若近期原文已经占满预算，仍需缩短材料或拆分任务，不会偷偷删历史。

## 2. 从哪里读起

| 文件 | 作用 |
| --- | --- |
| app/services/context_manager.py | prepare 判断是否超限；_prepare_long_input 分配预算、调用精简器、重新计数并返回 |

### ContextManager 具体做什么

```python
if required_tokens > self.max_input_tokens:
    return await self._prepare_long_input(history, summary)
```

这里的 required_tokens 是“系统提示词 + 当前问题”的占用。它不是用户登录 Token，也不是当前会话 ID。

_prepare_long_input 先创建 list(history)。这会产生新的外层列表，暂时复用原来的不可变消息对象；需要替换最后一条时，新建 ContextMessage，而不改原对象：

```python
current = history[-1]
working_history = list(history)
working_history[-1] = ContextMessage(
    current.seq,
    current.role,
    COMPRESSED_INPUT_PREFIX + compressed,
)
```

例如原来是 ContextMessage(13, "human", "几万字原文……")，副本最后一条仍然是 seq=13、role="human"，只是正文改成本次精简稿。history[-1] 仍保留几万字原文。这里没有访问数据库；以后由聊天服务保存原文，不能保存精简稿来覆盖聊天记录。

target_tokens 根据完整历史的基础占用计算，保留 32 的额外余量，并暂时复用 max_summary_tokens 作为本次问题的精简目标上限。这个上限与旧摘要生成仍是两种任务；之后可再拆成独立配置。余量只是保守预估，最终是否允许发送必须依靠完整请求重计数。

### ModelInputCompressor 具体做什么

1. 检查正文、目标预算和计数器返回值。
2. 若正文已经满足目标，直接返回，不调用模型。
3. 对包含系统提取提示和资料标记的完整请求计数，超限则按字符边界分块。每一块都必须在请求预算内；拼回首轮所有原始分块，应等于完整原文，不截掉尾部。
4. 顺序 await gateway.invoke(request, max_tokens=output_limit)，要求提取问题、必要材料、限制、待确认项，保留否定条件、数字单位、错误和必要代码。
5. 将本轮结果合并并重新计数；仍过长则有限次数再次精简。空结果、调用异常、无法缩小或达到次数限制时明确失败，不无限重试。

默认最多 3 轮、24 次网关逻辑调用、每轮 16 块、总等待 180 秒。单次输出默认最多 2048，网关允许的单次输出上限为 4096。网关底层 SDK 已有 max_retries=2，因此逻辑调用数不等于底层 HTTP 尝试数。后续正式接入时还需配置用户配额和费用限制。

精简模型的输入预算 max_request_tokens 与回答模型的应用预算分开配置。不能把供应商上下文窗口全部当作输入额度，必须预留输出、提示词和安全余量。

切块可能切开一句话或代码段，模型也可能遗漏语义；保留原文并不意味着精简稿无损。后续可以结合原文检索回查，提高对细节和指代的可靠性。本次没有声称已经完成 RAG。

## 3. 两个返回标志不能混用

```python
result.input_compressed   # True：本次问题使用了精简稿
result.was_compacted      # False：本次没有生成旧历史摘要
result.model_messages     # 本次准备交给回答模型的完整消息列表
result.summary            # 仍是传入的旧摘要或 None
result.input_tokens       # 最终完整输入的计数
```

长问题精简成功且完整输入不超过硬预算时，这个分支直接返回。即使仍在历史摘要的软触发阈值之上，也可继续本次回答；如果完整输入仍超硬预算且有可总结的旧片段，则复用 _prepare_history_context 生成旧历史摘要。后一种结果可能同时 input_compressed=True、was_compacted=True。

## 4. await、导入和异常

- asyncio 是 Python 标准库：asyncio.timeout 限制整个精简过程等待时间；超过时会取消正在等待的调用。用户主动取消产生的 CancelledError 继续向上传递。
- typing.Protocol 是标准库的接口约定，用来说明注入对象应提供什么方法，不会自动创建模型或保存数据。
- dataclasses.dataclass 是标准库，定义 ContextMessage 和 PreparedContext 这样的数据对象；frozen=True 防止给对象字段重新赋值。
- ModelGateway、TokenCounter、ContextMessage、PreparedContext 和各异常都是项目自己的模块或对象。
- ModelGateway 内部使用现有第三方 langchain_deepseek.ChatDeepSeek，ainvoke 是等待供应商回复的异步方法。本次没有新增第三方依赖。
- @logged_operation 是项目自己的装饰器，记录操作结果、耗时、代码位置和固定异常分类，不打印原始输入、精简结果、Key 或供应商响应正文。

同步的计数、构造对象、切片不写 await。compress 和 gateway.invoke 是异步函数，调用时需要 await；等待模型的这段时间事件循环可以执行其他请求。

ContextTooLargeError 表示预算无法满足，应提示拆分任务或调整服务端配置；InputCompressionError 表示精简器未配置、返回无效、超时或调用失败，应提示稍后重试或拆分任务。HTTP 映射尚未接入；当前错误不会自动成为新的接口响应。

## 6. 以后如何接入

创建真实 ModelInputCompressor 时，必须传入当前登录用户自己的 ModelGateway 和已适配的计数器，再通过 ContextManager(input_compressor=...) 注入。精简器不读取全局 Key、不创建共享账号、不关闭调用方拥有的网关；调用方应在整个精简及回答结束后统一关闭网关。

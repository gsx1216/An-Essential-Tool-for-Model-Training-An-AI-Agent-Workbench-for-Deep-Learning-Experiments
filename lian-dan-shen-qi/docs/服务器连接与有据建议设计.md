# 服务器连接、联网检索与有据建议设计

确认日期：2026-10-25。本文区分已完成基础和后续要求，不表示已连接用户的真实训练服务器或具备检索工具。

## 1. 用户明确要求

Agent 能通过后端工具连接训练服务器，读取训练运行、指标和日志；能联网搜索相近研究和技术资料；提出修改意见时必须有可核查依据，不能仅凭大模型自由发挥。

目前具备聊天、实验定义、运行记录，以及本人 SSH 配置管理与连接认证测试。私钥、带口令私钥及密码登录已通过本地真实 SSH 测试，细节见 [服务器连接配置与SSH工具基础说明](服务器连接配置与SSH工具基础说明.md)。Runner 已补充受控脚本启动、状态、停止和有界日志，经过本地真实 SSH/微型进程联调，详见 [Runner执行与状态日志说明](Runner执行与状态日志说明.md)；真实 Linux 服务器仍待验收。论文检索器、证据库和建议执行器尚未接入；不能将模型宣称“已经查过日志/文章”视为真实工具执行。

## 2. 远程服务器通过工具接入

```text
已认证用户 → 选择自己的服务器连接配置 → 后端连接适配器
                                        ↓
                         受控工作目录和已登记训练脚本
                                        ↓
                    启动运行 / 查询状态 / 读取日志 / 停止运行
                                        ↓
                    持久化 run_id、远端任务标识、指标与证据引用
```

连接信息属于用户/项目配置，后端验证归属。凭据由专门的安全配置保存，不混入 parameters_json、聊天、命令行日志或论文搜索请求。适配器接口与具体协议分开，首个适配器已采用 AsyncSSH，当前仅测试连接和认证。用户最终确认私钥登录，同时兼容密码；均要求用户名、IP、端口、可信主机指纹和 Linux 目录。部署者必须明确允许目标网段。没有真实目标和凭据时，不猜测并尝试连接。

Agent 调用结构化工具，例如 start_run、get_run_status、read_run_log、stop_run。实际执行由 Runner 负责，不让大模型直接拼接不受约束的 shell 命令。参数、可用脚本与目录在后端验证；工具返回真实结果和错误，模型不能自报成功。

运行必须有稳定的远端标识，重复提交不重复启动，网络中断后先核对原任务状态。长任务由心跳与轮询/事件恢复跟踪，不能只靠一次 HTTP 或 SSH 连接存活判断训练成败。原有创建请求幂等不等于远程进程已具备幂等，需要 Runner 单独实现。

## 3. 网络检索必须真正执行

为模型提供独立研究工具，由后端检索适配器实际发起网络请求。先从训练现象中提取通用检索关键词，例如方法名称、报错类别、优化器或指标趋势，不把完整私密日志、数据集内容和凭据上传到检索服务。

来源优先采用论文原文、作者/机构页面、官方文档和相关项目的官方仓库。相近论文可以提供方法线索，但任务、模型结构、数据规模和实验设置不一致时必须说明差异。搜索结果标题或摘要不能冒充已经阅读完整论文。

保存检索时间、标题、作者/机构、年份、URL/DOI 或论文编号，以及实际读取的证据片段/章节。区分只看到元数据、读到摘要、读到正文等证据范围。检索失败、正文不可访问或来源相互矛盾时如实说明，不编造标题、作者、结论和链接。

检索供应方可替换，先评估可免费使用的官方开放接口，遵守其配额与使用条件；项目不自动开通付费搜索、购买额度或注册收费服务。当前尚未选定或验证供应方，接入时需核对当时官方文档。测试先使用模拟检索，不产生收费调用。

网页、论文与日志内容都属于待分析资料，不得作为执行系统操作的高权限指令。研究工具读取公开资料，命令执行由独立受控工具处理。

## 4. 建议必须建立证据链

每条可执行修改提案应包含：

| 字段 | 要求 |
| --- | --- |
| 关联运行 | run_id、结果报告版本、配置/代码版本引用（后者由执行阶段补齐） |
| 本地观察 | 哪些 step/epoch/指标/日志位置支持发现，而非只写“模型可能不好” |
| 外部依据 | 可核查的论文/官方资料来源、相关结论和实际读取位置 |
| 适用条件 | 文献实验与当前实验有哪些相同点和差异，不能盲套结论 |
| 判断 | 分开描述已观测事实、推断、仍需验证的假设和反面证据 |
| 修改范围 | 具体参数或代码位置、建议差异及相关限制 |
| 验证方案 | 与什么基线比较、保持哪些条件、观察哪些指标、如何判断有无改善 |
| 实际执行 | 提案、应用后的 diff 和后续 run 分开记录，不能把“建议”写成“已修改” |

模型提出的原因本身不是事实。没有足够日志、指标或外部依据时，输出“待补充证据/待验证假设”和下一步采集方案，不能输出冒充已证实的改动结论。纯配置或接口错误可以引用实际错误和适用官方文档，不强行附上一篇不相关论文。

自动应用的提案应先通过后端结构与证据引用校验，确认引用确实来自工具返回的已保存证据。引用存在不代表因果成立；建议效果仍须用受控对照实验验证。证据不足的提案不能被自动应用策略当作已通过的修改。

## 5. 与全新聊天结果问答结合

用户在新聊天问“最近一次训练怎么样”，先使用本人范围的运行查询，读取报告与日志，给出有依据的结果说明。用户再问“有什么相关方法可以改善”，触发研究检索，结合当前证据形成建议，并返回可打开的来源链接。

回复至少明确：讨论哪次运行、实际观察到了什么、相关资料说明什么、当前推断是什么、准备如何验证。搜索无结果或网络断开时，保留本地证据，明确当前建议的验证状态，不伪造联网检索成功。

## 6. 必须通过的验收

1. 服务器连接成功、失败、超时、断线恢复都由真实工具状态反映；用户不能操作别人的连接或运行。
2. 重复启动请求不会产生两个训练任务；日志读取有范围、预算和受控路径。
3. 文献引用可回溯到实际检索/读取结果；故意给出不存在的引用时能被后端拒绝。
4. 没有依据、只读到摘要、资料冲突、模型无法联网时均诚实表达，不伪造出处。
5. 有证据的建议仍需记录基线、变更和验证运行；未通过策略的提案不自动应用。
6. 持久化日志不包含连接凭据、模型 Key、原始私密材料；工具失败不丢失训练结果。

实施顺序：运行记录（已完成）→ 服务器配置与 SSH 认证适配器（已完成基础）→ Runner 与运行绑定（基础完成，本地验证）→ 指标/报告与会话工具 → 研究检索和证据引用 → 建议与实际修改追踪。每步生成模块文档，并分别验证；整条闭环未接通前不宣称这些能力已上线。

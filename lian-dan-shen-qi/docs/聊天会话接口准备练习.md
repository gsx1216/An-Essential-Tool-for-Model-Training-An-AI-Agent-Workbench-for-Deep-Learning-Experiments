## 再写数据结构：TODO 4～7

位置：`app/api/schemas.py` 最下面新增的三个类。

| 类 | 需要填写的字段 | 用途 |
| --- | --- | --- |
| CreateSessionRequest | title：str，默认“新聊天” | 接收创建请求 |
| SessionCreatedResponse | session_id：str | 创建成功后返回 UUID |
| SessionResponse | session_id：str、title：str | 会话列表中的每一项 |

CreateSessionRequest 的 `model_config = ConfigDict(extra="forbid")` 已写好。它表示拒绝未声明字段，例如客户端提交 user_id，后续接口会返回安全的 422，而不是让客户端决定归属。

这不替代身份验证。客户端是谁，仍要通过 Token 查询确认。标题是否合法仍由业务服务检查。

类中的 pass 只是“这里暂时没有语句”的占位，可以在填写字段后删除；它不像 NotImplementedError，不会主动抛出异常。

为什么创建响应只返回 session_id：当前创建服务返回 UUID，标题可能已规范化；列表接口读取数据库中保存的标题。创建路由不应随便把未经规范化的请求标题当成已保存内容返回。

## 相关模块和导入对象

| 对象 | 来源 | 本次作用 |
| --- | --- | --- |
| lru_cache | Python 标准库 functools | 缓存无参数工厂返回的协作者对象 |

| SessionRepository | 项目仓储模块 | 提供聊天会话的数据库操作 |
| ChatSessionService | 你完成的业务模块 | 校验输入、异步调度仓储、组织结果或异常 |
| BaseModel | 第三方 Pydantic | 声明 HTTP 输入与输出的数据字段 |

dependencies.py 管理对象的组装；schemas.py 声明数据结构。它们不负责签发 Token，也不直接决定哪个用户能读取或删除某条聊天。

## 下一次接路由时的完整流程

```text
请求携带 Token
  → 身份依赖确认 current_user
  → 请求模型解析输入
  → Depends(get_chat_session_service) 提供服务
  → 路由将 current_user.user_id 交给业务服务
  → 仓储和 SQL
  → 路由使用响应模型返回结果
```

上图展示各环节职责，身份依赖、请求解析和对象依赖的具体解析次序由 FastAPI 管理；接口函数在需要的依赖与输入都成功解析后执行。

之后将接入三个接口：POST /sessions 创建，GET /sessions 列表，DELETE /sessions/{session_id} 删除。用户归属只来自认证身份，删除同时清理消息和轮次。

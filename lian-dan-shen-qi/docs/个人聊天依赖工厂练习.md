## 为什么需要工厂

UserChatService构造时需要两个协作者：UserModelGatewayFactory和MessageRepository。前者需要已组装的ModelCredentialService，后者需要后端数据库密码。把这些步骤集中在dependencies中，路由只需要通过Depends取得服务，不必重复组装。

```text
get_user_chat_service()
  → 读取后端MySQL密码
  → 调用已有get_model_credential_service()
  → 创建UserModelGatewayFactory，交给它凭据业务
  → 创建MessageRepository，交给它数据库密码
  → 创建并返回UserChatService

将来的聊天路由
  → Depends取得UserChatService
  → 另一个身份依赖验证Token，取得真实用户ID
  → await service.send_message或retry_message
  → 到这时才按本次用户读取Key、创建网关并执行聊天
```

组装服务和处理某个用户的请求是两个阶段。工厂不接收user_id、Token、session_id或个人Key，也不调用create_for_user、get_api_key、send_message或retry_message。

## 缓存什么，为什么不会串用户

`@lru_cache(maxsize=1)`复用本进程成功组装的UserChatService。它持有的是网关工厂和仓储；不持有本次用户ID、个人Key或正在使用的网关。各次发送/重试把身份作为方法参数传入，再按用户创建本次网关。

缓存不是保存所有用户的聊天数据，也不表示整个k8s集群只有一个对象。每个worker进程独立组装、独立缓存。配置发生变化需要重启相应服务进程，使缓存的协作者重新组装。

构建抛异常时，lru_cache不保存这次失败。配置修好后，可以重新尝试。这里缓存的是同步函数返回的服务对象，不是协程对象。

## 配置错误如何处理

外层读取数据库密码或组装时抛出的ValueError，由已提供的except记录安全日志，转换为HTTP 503“请稍后重试。”。

已有get_model_credential_service会处理数据库密码和主密钥配置错误，并抛HTTPException。它的503直接向上传递，不需要这里再次读取主密钥或重复记录相同异常。

依赖组装失败时，FastAPI不会进入路由处理函数。未知异常仍由已有请求中间件转换为通用500；本工厂不把编程错误全部伪装成配置错误。

## 模块、包和对象的职责

| 来源/对象 | 用途 |
| --- | --- |
| 标准库functools.lru_cache | 复用本进程组装成功的服务对象 |
| 标准库logging | 创建模块日志对象，供失败记录使用 |
| 第三方FastAPI.HTTPException | 把已知配置问题转换为安全的503响应 |
| 第三方FastAPI.Depends | 后续路由声明依赖，框架调用工厂并注入返回对象 |
| 项目get_mysql_password | 读取后端数据库连接配置，不从普通用户请求接收 |
| 项目get_model_credential_service | 组装凭据仓储、加密器和凭据业务；本次直接复用 |
| 项目UserModelGatewayFactory | 在实际聊天时，按用户读取个人Key并创建新网关 |
| 项目MessageRepository | 提供会话归属校验、消息和轮次的数据库操作 |
| 项目UserChatService | 协调个人网关创建和原有聊天、重试流程 |
| 项目log_failure | 记录异常类别、位置与请求标识，不记录配置内容 |

它们是对象之间的组合关系，不是继承。类型标注 `-> UserChatService` 表明函数应该返回什么，不会替你自动创建对象。

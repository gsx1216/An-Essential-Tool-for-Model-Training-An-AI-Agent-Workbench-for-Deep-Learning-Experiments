# 48K 上下文预算调整与报告查询验证

日期：2026-10-27。项目：`E:\code\LangChian_New`。

## 1. 本次问题与原因

用户在已有聊天里输入“查看报告”后出现上下文过长。实际日志在 `context_manager._prepare_history_context` 抛出 `ContextTooLargeError`，说明超限发生在准备历史阶段，还没有进入报告查询工具。

原先 `ContextSettings` 的输入上限和单次请求上限都是 12,000。聊天服务启用训练工具后预留 9,000，因此留给系统提示词、已有摘要、最近原文和当前问题的空间只有 3,000。即使当前问题很短，最近几轮回答累计起来也可能超过这个值。原逻辑要求保留最近四轮，不会为了通过预算而偷偷删掉这些原文，因此返回了超限提示。

## 2. 新配置与单位

| 配置 | 原默认 | 新默认 | 用途 |
| --- | --- | --- | --- |
| `CHAT_MAX_INPUT_TOKENS` | 12000 | 49152 | 应用完整输入预算，包含工具占用 |
| `CHAT_MODEL_REQUEST_TOKENS` | 12000 | 49152 | 正文、摘要和问题精简调用使用的单次请求预算 |
| `CHAT_COMPACT_AT_TOKENS` | 9600 | 39321 | 较早历史摘要的触发阈值，约为总预算的 80% |
| 最近保留轮数 | 4 | 4 | 最近原文与当前问题继续保留 |
| 摘要预算 | 2000 | 2000 | 摘要长度目标不变 |
| 网关最大输出 | 4096 | 4096 | 模型输出 token 上限，与输入预算分开 |

这里 48K 使用 `48 × 1024 = 49152`。必须区分：当前 `Utf8BudgetCounter` 按 UTF-8 字节长度加消息开销估算，工具循环按 JSON 序列化后的 UTF-8 字节估算；变量虽然保留 tokens 命名，这不是 DeepSeek 精确 tokenizer，也不是计费依据。中文一个字符可能占多个 UTF-8 字节，所以不能承诺可放入 49,152 个实际模型 token。真实供应商上下文能力还需满足模型自身限制，不能通过修改应用配置扩容供应商模型。

本次不更换 tokenizer、不下载模型文件、不新增第三方依赖；先修复应用输入预算过小的问题。后续若要按供应商精确 token 管理，应为正文、工具定义、工具调用、摘要和问题精简统一接入相同 tokenizer，并考虑供应商消息模板及输出余量。

启用训练工具时，历史准备的实际硬预算为 `49152 - 9000 = 40152`。工具定义、策略提示、返回结果等与历史共同受最终 49,152 预算约束。工具的调用次数、日志片段大小、报告分页、结果截断上限继续保持原来的限制，扩大输入预算不会取消这些保护。

## 3. 调用流程与模块职责

1. `app.config.get_context_settings()`：python-dotenv 加载后端 `config/.env`，环境变量优先，校验数值，构造部署配置。配置不接收普通用户 API 输入。
2. `app/models/context_settings.py`：dataclasses 不可变配置；新增共享默认常量，统一 48K 和摘要触发阈值。
3. `app/services/user_chat_service.py`：持有部署配置，组装当前用户的网关和本次聊天服务，不共享个人 Key。
4. `app/services/chat_context_factory.py`：为本轮创建上下文对象；取两个输入上限的较小值，再扣除工具预留量。调用前的任务有效性校验继续执行。
5. `app/services/context_manager.py`：计算系统提示、历史摘要、近期原文、当前问题的占用；超过阈值时总结较早历史，保留最近四轮及当前问题。直接实例化时也使用同一套新默认值。
6. `app/services/read_only_chat_service.py`：进入模型工具循环，按需查询真实报告，结果再次计数并审计；不会因一句“查看报告”自动开始训练。
7. `app/services/model_gateway.py`：复用 LangChain / ChatDeepSeek 发起模型调用，最大输出仍为 4096。

已有摘要、会话归属、序号缺口、租约、原始消息持久化、训练幂等逻辑不需要修改。仍然无法容纳的必要上下文会明确报错，不会无限发给模型或伪造丢失内容。

## 4. 如何生效

本机 `config/.env` 以及当前检查进程环境中没有上述预算覆盖，因此更新代码后采用新默认值；本次没有修改含密码和密钥的 `.env`。

如需在另一个部署环境明确设置，可添加：

```dotenv
CHAT_MAX_INPUT_TOKENS=49152
CHAT_MODEL_REQUEST_TOKENS=49152
CHAT_COMPACT_AT_TOKENS=39321
```

两个输入上限都要检查，只提高其中一个会被另一个较小值限制。进程环境变量优先于 `.env`。API 依赖对象存在进程内缓存，因此保存后需要重启 API；多副本部署需要更新所有 API 副本。监控 Worker 不负责聊天上下文，不需要为这次调整重新训练或重建数据表。

在项目根目录查看实际加载的非敏感配置：

```powershell
python -c "from app.config import get_context_settings; s=get_context_settings(); print(s.max_input_tokens, s.model_request_tokens, s.compact_at_tokens)"
```

预期：`49152 49152 39321`。

## 5. 在 /docs 重新验证

1. 停止旧 API 进程，重新执行 `python -m uvicorn app.main:app --reload`。
2. 登录并 Authorize；使用原来的聊天会话即可，不必删除历史。
3. 上一次“查看报告”已经记录为待重试时，调用 `POST /sessions/{session_id}/retry`，不填写请求体；它重试原来待回复的问题，不是重新开始训练。
4. 已成功回复、当前没有待重试轮次时，使用消息接口发送新的查询并生成新的 request_id。
5. 观察 `/sessions/{session_id}/tool-calls`。报告尚未生成时，模型应说明报告不存在；没有绑定运行时，可以明确询问“我最近一次训练的报告是什么”。这是事实状态问题，与上下文超限分开处理。
6. 训练中的后台监控仍由 Worker 采集。不要为了查看报告反复提交新的训练指令。

本次没有新增或更改 API 路径、请求体和响应结构，不需要重新导出 OpenAPI。

## 6. 验证范围

上下文与聊天工具相关单元回归共 130 项通过。新增 7 项覆盖：

- 48K 默认值、共享默认常量与 9K 工具预留。
- 环境变量覆盖及两个上限取较小值。
- 约 24K 近期历史超过旧预算，在新预算下保留原文并进入报告工具、得到回答。
- 显式恢复旧小预算时能够复现原错误。
- 新阈值下自动总结较早两轮，保留最近四轮及当前问题。
- 超出新预算时仍保护必要原文，输入列表不被修改。
- 工具完整请求仍执行最终硬预算检查。

测试使用真实本地计数器、上下文管理器、工具循环及模拟报告/模型，不调用真实模型、不连接训练服务器、不启动 GPU 训练，不产生模型费用。真实供应商返回及本人聊天数据需按上面的步骤继续验收。

# 训练指标采集与事实报告说明

日期：2026-10-26。项目：`E:\code\LangChian_New`。

## 1. 本阶段完成什么

训练脚本可以在普通 stdout/stderr 中输出 JSONL 指标。后端通过已鉴权 Runner 读取真实远端日志，按字节游标增量解析，保存指标及采集状态，提供分页/最新统计，并生成可复用、带版本和完整性说明的事实报告。

新增三个共享表 run_metric_streams、run_metric_events、run_reports，目前容量诊断跟踪十四张业务表。没有按用户动态建表，没有清空原有数据，没有修改 .env、启用样例注册表或调用收费模型。

新增 39 项单元测试，完整 893 项通过。9 组新 HTTP/MySQL/真实回环 SSH/微型进程联调通过，Runner 8 组、运行记录 15 组、容量 8 组、上下文聊天 16 组回归通过。联调是在 Windows 兼容分支运行微型进程，没有执行 GPU 训练；真实 Linux 和用户训练服务器仍待验收。

当前通过显式 sync 接口采集，没有自动后台轮询。报告生成和读取不连接 SSH，也不调用大模型。模型解释、聊天训练工具、Skill、论文 RAG 仍是后续阶段，不把一份事实报告当作已经实现分析 Agent。

## 2. 最短使用路径

```text
注册/登录 → 保存本人服务器配置 → 创建实验与运行 → start
    → refresh 查看状态
    → metrics/sync 采集指标，可在运行中重复调用
    → metrics 或 metrics/latest 查询
    → POST report 生成报告 → GET report 查看
```

如果只生成报告、尚未采集指标，也允许返回报告，但明确标注 NOT_SYNCED、NO_METRICS 和 SOURCE_INCOMPLETE，不伪造 loss=0。若刚刚开始采集一个大日志，max_pages 用完仍没追上来源，需要继续 sync；caught_up 表示追上本次读取时的日志，不等于训练已经结束。

## 3. 训练脚本怎么输出指标

每条指标单独占一行，使用 json.dumps，并 flush，避免普通进度条混在同一行：

```python
import json

print(json.dumps({
    "type": "metric",
    "split": "train",
    "step": 100,
    "epoch": 2,
    "loss": 0.35,
    "accuracy": 0.82,
}), flush=True)
```

普通 `print("loading data")` 仍是日志，不被当作指标。这里的 loss/accuracy 是训练脚本自己上报的数值，采集成功不等于系统独立验证了训练计算正确。

| 字段 | 规则 |
| --- | --- |
| type | 必须为 metric；其他合法 JSON 对象按普通日志处理 |
| step | 必填非负整数，最大 2^53-1，不接受 bool 或字符串 |
| epoch | 可省略或 null；有值时同样是非负整数 |
| split | 默认 train；允许 train、validation、test |
| 其余字段 | 1～16 个数值指标；名称为小写字母开头，随后小写字母/数字/下划线，最多 64 字符 |
| 指标值 | 有限 int/float，绝对值不超过 1e100；不接受 null、bool、字符串、NaN、Infinity |

不强制 accuracy 一定在 0～1，因为有的脚本使用百分比；具体量纲和优劣方向仍应由任务定义。分组必须写明，不能把训练与验证集的同名 loss 混成一条曲线。step 回退保留原事件并记录 STEP_REGRESSION，不丢弃、不补号；“最新值”按源文件位置判断，不是挑最大的 step。

单行最多 8192 字节，每次读最多 16384 字节，每个 run 最多接纳 64 个 split/name 系列。超长行只记一次 oversized，跨页继续丢弃直到下一换行，再恢复解析。以 `{` 开始但 JSON 损坏的行记 invalid；普通文本记 ignored。重复 JSON 键也拒绝，避免同一行两个 loss 的歧义。

## 4. 五个新接口

| 方法与路径 | 输入与行为 |
| --- | --- |
| POST /runs/{run_id}/metrics/sync | max_pages 默认 4，范围 1～8；每页最多 16 KiB，从服务端保存的游标继续 |
| GET /runs/{run_id}/metrics | after 默认 -1，limit 默认 100、最大 500；可按 split、metric_name 筛选 |
| GET /runs/{run_id}/metrics/latest | 每个分组/指标的 first、last、min、max、points 等已采集数值统计 |
| POST /runs/{run_id}/report | 基于当前已采集数据生成或复用最新事实报告，不自动 sync |
| GET /runs/{run_id}/report | 读取已存报告；没有则 404，有则返回 is_stale，不自动重建 |

这些接口都需要 Bearer Token，run_id 必须属于当前登录用户。没有“客户端上传一批指标直接入库”的接口。客户端传 user_id 不会改变身份，普通用户不能输入 SQL、远端任意路径或改写全局配置。

分页返回 next_offset，只在确实还有下一页时提供；下一次把它传入 after。这个游标是原始日志行起始字节位置，不是 step，也不是列表下标。同 step 多条物理事件会保留；重复采集同一物理行才去重。

sync 返回 revision、pages 和公开 stream 状态，包括 offset、valid/invalid/ignored/oversized、series、regressions、complete、caught_up、truncated、stale 等。不公开内部半行内容或尾部字节缓冲。

## 5. 从 Token 到数据库，依次如何校验

```text
metric_routes 路由
  → Depends(require_current_user)
      → get_bearer_token 只提取 Bearer Token
      → CurrentUserService/登录仓储验证有效登录，取得系统 user_id
  → Depends(get_metric_service)
      → 读取部署 MySQL 密码，构造仓储；不在工厂中读取个人数据
      → 只保存 Runner 工厂引用，普通读取无需解密主密钥或 SSH
  → MetricService.sync(user_id, run_id, max_pages)
      → 校验 ID 和页数 → 在线程读取本人采集快照
      → 此时才取得 Runner，调用本人日志工具
      → Runner 校验执行绑定、服务器归属、配置绑定、凭据和主机身份
      → 取得原始字节和文件边界证据
      → 解析一页 → 短事务校验版本、插入事件、保存游标
      → 达到页数预算或追上来源后返回
```

MySQL 驱动是同步的，通过 `await asyncio.to_thread(...)` 放在工作线程；SSH 是 AsyncSSH 异步操作。数据库事务不会跨 SSH 网络等待持锁。

## 6. 为什么需要原始字节和半行缓冲

旧日志接口为了展示，把字节按 UTF-8 解码，截在中文中间时会产生替换字符，不能再准确还原原始指标。因此本阶段扩展 Runner 日志协议，增加 raw_base64、log_size、anchor_sha256、source_changed。展示 content 仍保留，旧接口主体和游标语义不变。

RunnerTransport 验证 Base64、字节长度、下一游标、展示文本及范围，再把原始字节交给采集器。读取限定在本次捕获的文件大小以内，避免日志恰好追加时，数据跨过自己声明的边界。

例如第一页末尾为 `{"type":"metric","step":1,`，不能立刻记为错误。先把这段原始字节存进 pending；下一页收到 `"loss":0.3}\n` 再组成完整行。只有可信终态、追到 EOF 且日志未截断，才允许解析没有换行符的最后一条完整 JSON。运行中、来源 stale 或日志截断时，不猜测半行已经结束。

## 7. 去重、并发与回滚

run_metric_events 的主键为 (run_id,source_offset)，同一条物理来源不会重复写入。run_metric_streams 保存游标、pending、尾部字节、计数、系列和 revision。

采集先读取快照，再出事务连接 SSH；写回时锁住本人 run 行，重新比较 revision。若其他请求已经推进，当前结果不写入，重新读取最新快照，最多冲突重试 3 次。事件 INSERT 和游标更新在同一事务提交：中途失败两者一起 rollback，避免“游标过去了但事件没保存”。不使用 INSERT IGNORE 掩盖异常。

写入还核对计数不回退、valid 增量等于事件数、事件位置严格前进且与原始缓冲边界相符。正常重复 sync 没有新增内容或质量变化时，不增加 revision。

读取时校验游标/报告摘要、来源位置、字段结构和数值；已存数据异常返回通用 503，不把损坏数据偷偷转换成 0。

## 8. 来源变化怎么处理

读取时核对游标前最多 128 字节的 SHA256 边界。如果远端文件短于已保存游标，或该边界已变化，返回 409，保留原指标，并在短事务中将最新采集状态标为不确定，让旧报告变为 is_stale=true。不会自动清空重采或换成另一份日志。

远端任务 missing 返回 502，并标记来源不确定；SSH 网络错误不直接改训练成败。已完成并持久化的历史报告仍可离线读取。

边界检查用于检测常见截断/替换，不是整份历史日志的密码学防篡改证明。相同服务器账号拥有文件权限，不构成不可信代码沙箱；需要不可变证据归档时，后续应保存完整对象及内容摘要。

## 9. 报告是什么，怎样更新

报告包含运行/实验身份、参数、状态、退出码、安全错误码、UTC 起止观测时间、已采集字节位置、有效/错误/忽略/超长/回退计数、每个指标系列的首末值、最小最大值、点数和 delta=末值-首值。

它不判断“下降就是改善”“已经收敛”“一定过拟合”，也不根据无依据的文字猜异常原因。模型解释将来必须在这份事实和具体日志之上进行，不替代数据采集。

| 标记 | 含义 |
| --- | --- |
| NOT_SYNCED | 尚无采集状态 |
| NO_METRICS | 尚无有效指标，不能据此把指标当成 0 |
| SOURCE_INCOMPLETE | 未确认终态完整来源，或尚未追完/日志截断 |
| INVALID_LINES | 有格式或数值无效的结构化行 |
| OVERSIZED_LINES | 存在超出行预算的内容 |
| STEP_REGRESSION | 同 split 的 step 出现回退，事件仍保留 |
| LOG_TRUNCATED | 达到 Runner 日志预算，后续指标可能没有保存 |
| STALE_SOURCE | 来源过期、缺失或检测到变化 |
| PENDING_TAIL | 仍有未能确定完整的末尾内容 |

collection_complete 表示来源已确认结束并采完、未截断，不代表指标本身没有错误或训练效果良好；仍需看 warnings。脚本 succeeded、采集完整、数据质量可靠是三个不同维度。

生成报告时对本人 run 加短锁，在一致数据版本上聚合并保存。相同 source_revision 和运行状态签名复用原报告，不增加版本；采集数据/质量或运行状态变化后，GET 返回旧报告并标记 is_stale，POST 才生成新版本。运行 result_ref/result_version 与报告同事务更新；已存在报告的版本与运行引用不一致会拒绝读取。

当前只保存最新报告快照及版本号，不保留每个旧版本全文。generated_at 是生成时间；运行起止仍是后端观测的 UTC 时间，不冒充精确远端时钟。

## 10. 三张表与 SQL 文件

| 表 | 存储内容 |
| --- | --- |
| run_metric_streams | 每个 run 的 revision、字节游标、有限缓冲/质量状态及摘要、更新时间 |
| run_metric_events | 原始行位置、step、epoch、split、数值 JSON、采集时间 |
| run_reports | 最新版本、来源 revision、运行状态签名、事实 JSON/摘要和生成时间 |

三张表都用 (run_id,user_id) 复合外键指向 experiment_runs，数据库也拒绝跨用户归属。事件保留原位置，报告不保存整份训练日志。索引按 run 和 split/offset 支持有界查询。

| SQL | 作用 |
| --- | --- |
| create_run_metric_streams.sql | 游标表、预算与外键 |
| create_run_metric_events.sql | 事件表、去重主键和分页索引 |
| create_run_reports.sql | 最新报告表、版本及大小约束 |
| lock_metric_run.sql | 本人运行读取/短事务锁与报告输入 |
| get_metric_stream.sql | 读取本人游标和质量快照 |
| save_metric_stream.sql | 更新原子游标状态 |
| save_metric_event.sql | 保存物理来源唯一事件 |
| list_metric_events.sql | 按位置、分组和指标名分页 |
| aggregate_run_metrics.sql | JSON_TABLE 展开指标，窗口函数取首末，按系列统计 |
| get_run_report.sql | 读取本人最新报告 |
| save_run_report.sql | 写入或替换最新报告及版本 |
| link_run_report.sql | 同事务更新 run 的报告引用 |

聚合 SQL 设 5 秒执行预算，最多返回 65 行，用来检测是否超过 64 系列限制；不是无限扫描全部用户。实际使用 MySQL 8.0.46 验证，语法参考 [JSON_TABLE](https://dev.mysql.com/doc/refman/8.0/en/json-table-functions.html) 和 [窗口函数](https://dev.mysql.com/doc/refman/8.0/en/window-function-descriptions.html) 官方文档。

## 12. 在 /docs 里手动测试

项目根目录、已有 langchain 环境执行：

```powershell
python -m app.database --metrics-schema
python -m uvicorn app.main:app --reload
```

需要先完成 Runner 阶段迁移。--metrics-schema 只创建三张新表，不启动脚本、不回填旧聊天；MySQL DDL 有隐式提交，不承诺三条建表语句组成可回滚大事务，修正失败原因后可幂等重跑。

准备真实服务器后，将 examples/metric_smoke.py 放在本人工作目录，在部署者的活动注册表中合并 config/metric_scripts.example.json 的条目，核对字节哈希，重启后端。样例没有被本次开发自动启用。

登录 Authorize 后，创建实验与 run，parameters 可以是 `{"steps":3,"delay_seconds":0.2}`；调用 start，选择 metric_smoke。然后按顺序：

1. refresh 查询运行状态。
2. POST metrics/sync；若 caught_up=false，继续调用。
3. GET metrics 查看原始事件；GET metrics/latest 查看各组统计。
4. POST report 生成；GET report 检查 version、collection_complete、warnings 和 is_stale。

想接入真实训练，把示例 print 放入训练循环相应位置即可；不要把示例公式当作真实 loss。没有经过结构化输出的旧日志如 `loss=0.3`，当前不通过正则猜数值；报告会说明无指标。

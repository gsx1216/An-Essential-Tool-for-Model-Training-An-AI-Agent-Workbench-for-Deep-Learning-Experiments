# 数据校验说明

这次修复的是“用户不存在，仍然能创建引用该用户的会话”的问题。

输入 `2` 不会自动创建 users 表里的用户。原先只是把数字 2 保存到 chat_sessions.user_id；因为没有检查 users，也没有会话到用户的外键，所以出现了无效归属。仅检查数字格式，或仅按 user_id 筛选会话，都不能证明用户真实存在。

## 现在的校验

| 操作 | 校验规则 |
| --- | --- |
| 创建用户 | 用户名必须是非空字符串，去除首尾空白后不超过 64 个字符；重名由数据库唯一索引拒绝，并转换为易懂的错误 |
| 创建会话 | 用户 ID 必须是正整数；必须在 users 表中找到该用户；标题去除首尾空白后为 1～200 个字符 |
| 查询会话列表 | 先确认用户存在，再筛选该用户的会话 |
| 查询指定会话 | 检查用户存在、UUID 格式和会话归属；用户存在但会话找不到或属于别人时返回 None |
| 保存提问 | start_turn 校验用户、会话归属和非空正文，原子提交提问与 pending 轮次；同一会话不允许两个未完成轮次 |
| 保存回复 | complete_turn 校验本次生成任务和消息顺序，原子提交回复与完成状态；失败不删除先前已保存的问题 |
| 读取消息 | 必须同时提供用户 ID 和会话 ID；确认用户与会话归属，查询也按用户过滤 |

start_turn 固定保存 human 消息，complete_turn 固定保存 ai 消息；系统提示词只加入模型请求。seq 由仓储读取数据库当前序号分配，不再要求服务传入 start_seq。正文不会被 strip 修改，以保留代码缩进和换行。

## 几个关键概念

- `ValueError`：输入不合法或业务条件不成立，立即停止当前操作。
- `raise`：抛出错误；后面的插入和提交不会继续执行。
- `try / except`：测试入口接住可预期的错误，并显示“操作失败：用户不存在”等信息。
- `commit()`：确认保存当前事务里的修改。
- `rollback()`：操作失败时撤销当前事务中尚未提交的修改。回复写入失败只撤销本次回复和状态变化，先前已经提交的提问保留。
- `_require_user()`：真正查询用户表，确认用户存在；以单下划线开头表示供类内部使用。
- `FOREIGN KEY`：数据库层的关联约束。即使绕过 Python 直接执行 SQL，也不允许填写不存在的非空 user_id。
- `FOR UPDATE`：保存消息时短暂锁住该会话行，让同一会话的消息按顺序写入；提交或回滚后释放。这里不会在等待模型回复时持有锁。

## 如何运行

先在项目根目录、langchain 环境中运行只读检查：

```powershell
python -m app.database --check-user 2
```

它从后端配置加载 MySQL 密码，显示用户 2 是否存在，以及哪些会话关联了不存在的用户。这个命令不修改数据。

然后补齐数据库约束：

```powershell
python -m app.database
```

已有表不会被 CREATE TABLE IF NOT EXISTS 自动更新，因此初始化代码会单独检查、补加外键。已有外键则跳过，允许重复运行。

如果已有会话指向不存在的用户，默认初始化会停止并显示原因，不会擅自删除记录、创建假用户或把它分配给其他用户。

若要保留这些会话和消息、取消错误归属，再补外键，运行：

```powershell
python -m app.database --repair-orphan-owners
```

该命令会先把涉及的会话 ID、原 user_id 和标题备份到 data/migration_backups/session_owners_*.json，备份成功后才把已确认无效的归属设为 NULL。它不会删除会话或消息。NULL 表示暂未分配用户，这些记录不会出现在任何普通用户的会话列表里。后续确认真正归属后再单独处理。

旧记录修复、DDL 建表或加约束并不是一个可以整体回滚的大事务。备份和数据修复会先完成并提交，然后添加外键；若外键添加失败，可先查看错误，保留备份后重试。

最后测试：

```powershell
python -m app.repositories.session_repository
```

若用户 2 不存在，输入 2 应输出“用户 ID 2 不存在”，不应再新增会话或输出成功的 UUID。

消息仓储的方法现在要求传入 user_id：

```python
turn_id = message_repository.start_turn(
    user_id=user_id,
    session_id=session_id,
    content="你好",
)
attempt_id, history = message_repository.claim_turn(user_id, session_id, turn_id)
message_repository.complete_turn(
    user_id, session_id, turn_id, attempt_id, "你好，有什么需要帮助？"
)
messages = message_repository.load_messages(user_id, session_id)
```

仓储不再提供 save_message 和整轮一起提交的 save_turn。save_message.sql 仍由 start_turn、complete_turn 复用。失败状态与重试机制见《可恢复对话开发说明.md》。

## 当前边界

当前是本地 CLI 教学阶段，手动输入用户 ID 用于测试，并不构成身份认证。正式接口里的 user_id 应从登录身份取得，不能直接相信客户端声明的身份。

chat_cli.py 已支持 MySQL 会话列表和历史读取。ChatService 已实现问题先保存、模型生成、失败记录和重试；下一步将它接入命令行聊天循环。

单元测试模拟数据库边界错误；scripts.verify_turns_mysql 通过后端配置连接真实 MySQL，在独立临时库验证完整存储和服务流程，不读取用户聊天正文。

## 1. 用户发出的HTTP请求长什么样

```http
POST /sessions/<已有会话ID>/messages
Authorization: Bearer <登录接口返回的access_token>
Content-Type: application/json

{
  "content": "请帮我分析这次训练",
  "request_id": "d5d2e70c-bd6b-40a0-9855-9066bc22a653"
}
```

会话ID来自创建会话接口，放在路径里；Token来自登录接口，放在请求头里；问题和请求去重ID放在JSON正文里。这三部分的数据来源不同。

新问题使用新request_id；同一个问题因网络问题重新提交时，保留原ID与内容。这个ID用于识别一轮请求，不负责证明用户身份。

## 2. 装饰器如何登记接口

```python
router = APIRouter(prefix="/sessions", tags=["聊天消息"])

@router.post("/{session_id}/messages", response_model=ChatReplyResponse, status_code=200)
```

APIRouter是FastAPI提供的路由容器。模块导入时，装饰器把函数登记到router：前缀与路径组合成POST /sessions/{session_id}/messages。tags决定/docs中的分组，response_model声明公开响应结构，status_code声明正常成功时使用200。

此时只是向router登记。主应用还要执行app.include_router(chat_router)，请求才能通过主应用匹配到它。装饰器不会在模块导入时发送问题或调用模型。

## 3. 接口的五个参数分别来自哪里

```python
async def send_chat_message(
    session_id: str,
    request: SendMessageRequest,
    response: Response,
    current_user: UserResponse = Depends(require_current_user),
    service: UserChatService = Depends(get_user_chat_service),
):
    ...
```

| 参数 | 谁提供 | 里面是什么 | 后续交给谁 |
| --- | --- | --- | --- |
| session_id | FastAPI从URL路径提取 | 待操作的会话ID字符串 | 聊天业务与仓储 |
| request | FastAPI根据请求模型解析JSON | content字符串、request_id UUID对象 | 当前路由 |
| response | FastAPI注入的Response对象 | 可以写入成功响应头的对象 | FastAPI合并到最终响应 |
| current_user | require_current_user依赖的返回结果 | 已确认的user_id、username | 路由取user_id传给业务 |
| service | get_user_chat_service依赖的返回结果 | 已组装的UserChatService实例 | 路由await调用它的方法 |

request在这里是你声明的Pydantic数据模型，不是FastAPI原始Request对象。response也不是用户提交的JSON，它用于设置返回给客户端的响应头。

类型标注负责说明数据结构。Depends负责让框架调用依赖并注入返回值；这不是继承。进入接口函数之前，FastAPI必须完成相关请求解析、字段校验与依赖解析。

## 4. require_current_user怎样确认当前用户

```python
current_user: UserResponse = Depends(require_current_user)
```

含义是：FastAPI先执行这个依赖链，成功后把结果放到current_user。依赖失败时不会执行接口中的聊天调用。

### 4.1 HTTPBearer只负责识别请求头

auth_dependencies.py中声明HTTPBearer(auto_error=False)。它识别Authorization头里的Bearer方式，提供HTTPAuthorizationCredentials对象，其中scheme是认证方式、credentials是原始Token字符串。

它还没有证明Token有效。随便写一个Bearer字符串也可能被提取，所以不能在这一步就相信用户身份。

### 4.2 get_bearer_token提取原始Token

这个函数依赖HTTPBearer的解析结果。缺少Bearer凭证时，抛HTTPException(401)，同时设置WWW-Authenticate: Bearer。存在凭证时，返回credentials.credentials。

它不查询数据库、不创建新Token，也不接受客户端另传的user_id。

### 4.3 require_current_user调用身份业务

它接收上一步的access_token，并通过另一个Depends取得CurrentUserService，然后执行：

```python
user_id, username = await service.get_current_user(access_token)
```

这里的service是身份业务；聊天路由参数中的service是UserChatService。同名局部变量处于不同函数中，指向不同对象，不能把它们当成同一个服务。

### 4.4 CurrentUserService验证格式并查询有效身份

它先检查Token为字符串，符合当前签发的43字符格式。格式不合法就抛InvalidTokenError。

然后调用TokenService.hash_token计算SHA-256哈希，得到64位小写十六进制字符串。数据库存的是这个哈希，不是原始Token。

接着执行await asyncio.to_thread(self.session_repository.get_active_user, token_hash)。仓储是同步MySQL操作，交给线程执行，避免阻塞事件循环。

### 4.5 LoginSessionRepository执行SQL

sql/get_active_login_user.sql查询login_sessions并关联users，同时检查：Token哈希一致、revoked_at为空、expires_at大于当前UTC时间，以及关联用户存在。

查询成功返回(user_id, username)，查询不到返回None。None由身份业务转成InvalidTokenError。校验不会重新签发Token，也不会延长原有到期时间。

### 4.6 转为HTTP结果

require_current_user把InvalidTokenError转成401；数据库错误转成通用503“请稍后重试。”。成功时构造UserResponse(user_id=user_id, username=username)。

所以current_user.user_id来自Token与数据库共同确认的身份。正文或URL查询参数中的user_id都不能覆盖它。

## 5. get_user_chat_service如何提供聊天业务

```python
service: UserChatService = Depends(get_user_chat_service)
```

工厂先读取部署者配置的MySQL密码，再调用已有get_model_credential_service取得凭据业务。凭据业务持有凭据仓储和使用固定服务端主密钥的加密器。

然后创建UserModelGatewayFactory，把凭据业务交给它；创建MessageRepository，把数据库密码交给它；最后创建UserChatService并返回。

这些构造步骤是同步的，所以工厂用def，不使用await。MessageRepository构造时只加载SQL，没有查询某个用户的消息。

@lru_cache(maxsize=1)复用本进程组装成功的业务对象。缓存中保存的是协作者，不是某个用户的Token、Key或网关。构建失败不缓存；各worker进程有各自的缓存。

服务端缺少配置时，工厂转换为503，聊天接口函数还没有执行。普通用户不用、也不能通过聊天正文提交数据库密码或服务器加密主密钥。

## 6. 请求模型怎样检查正文

SendMessageRequest要求content为str、request_id为UUID，两个字段都必填。Pydantic会把合法的UUID字符串解析成UUID对象。

ConfigDict(extra="forbid")拒绝额外字段。例如正文多传user_id、api_key或history会得到422。已有安全校验异常处理器不会把原始输入回显到错误响应。

这一步负责结构与类型。问题是否只有空白、是否超长，由业务层validate_message_content继续检查。

## 7. 你写的await调用把什么传下去

```python
reply = await service.send_message(
    user_id=current_user.user_id,
    session_id=session_id,
    content=request.content,
    request_id=request.request_id.hex,
)
```

user_id来自已认证身份；session_id来自路径；content来自已解析的正文；request_id.hex把UUID对象转为仓储需要的32字符字符串。这里不生成新ID。

send_message是async方法，调用它先产生协程对象；await才等待执行并取得回复字符串。如果少了await，reply就不是回复，查询、模型调用和保存也不会按预期完成。

await等待异步I/O时允许事件循环处理其他协程；它不自动让所有同步代码并发。同步数据库操作和网关构造在已有业务中通过to_thread处理，所以路由不再重复包一层线程。

## 8. UserChatService怎样用本人的Key

UserChatService先同步校验并规范user_id、session_id、content，然后进入async with self._open_chat(user_id) as chat。

_open_chat调用个人网关工厂的create_for_user(user_id)。它await凭据业务get_api_key(user_id)，后者按用户与供应商查询MySQL密文，再用加密器解密并核对密文绑定的用户ID。

没有配置就抛ModelCredentialNotConfiguredError；密文无法解密抛ModelCredentialDecryptionError。不会回退到共享Key。这些属于开始新轮次前的条件，失败时不保存本次新问题。

拿到原始Key后，工厂在线程中创建ModelGateway。需要区分两层同名属性：

| 对象 | gateway_factory属性里放的是什么 |
| --- | --- |
| UserChatService实例 | UserModelGatewayFactory实例，负责按用户读取Key |
| UserModelGatewayFactory实例 | 默认是ModelGateway类，用Key构造网关 |

_open_chat用本次网关和消息仓储创建ChatService。它们是对象之间的协作，不是类继承。

## 9. ChatService与仓储如何保证会话归属和消息保存

### 9.1 start_turn：先保存问题

ChatService调用仓储start_turn。仓储在事务中检查用户与会话归属，锁住该会话行，检查请求ID和当前未完成轮次，再保存human消息及pending轮次。

会话UUID格式合法不等于有访问权限。其他用户拿到这个UUID，仍然过不了这里的归属检查；模型不会被调用。

事务提交后用户问题已经存在。后面的模型异常不会把这条问题撤销。

### 9.2 claim_turn：领取处理权并读取新上下文

仓储领取这一轮的处理权，生成本次attempt_id并设置租约，再读取数据库中的当前消息。状态和attempt_id用来阻止同一轮同时生成或旧任务写回。

如果相同请求已经完成，ChatService读取已保存的回复返回，不再次调用模型。若请求处于未完成状态，按现有轮次与租约规则处理。

### 9.3 _build_model_messages：组装输入

ChatService添加system提示词，再追加仓储读取的历史。历史已经包含本轮用户问题，因此不再追加一次问题。

这里使用服务端最新历史，不复用浏览器GET接口展示的某一页。打开历史页面不会自动调用模型。

### 9.4 ModelGateway.invoke：实际模型调用边界

网关调用self.model.ainvoke(messages)。self.model由ChatDeepSeek构造，使用本人的Key。返回对象中的content成为回复，usage_metadata是用量信息；ChatService校验回复正文。

本次验证把这个网关替换成假对象，直接生成固定字符串；没有联系供应商，没有验证真实模型名称、Key可用性或计费行为。

### 9.5 complete_turn：保存回复

仓储再次在事务中检查会话归属、轮次和本次attempt_id，保存ai消息、完成轮次并更新时间。成功后ChatService才返回回复。

如果模型抛异常，ChatService调用fail_turn记录简短失败代码并保留原问题，再抛异常。数据库写回失败属于另一条分支，不因此自动重新调用模型。

## 10. 为什么return写在async with内也会关闭网关

UserChatService中的return await chat.send_message(...)先等聊天完成。在真正把结果返回上层前，Python还会退出async with，执行_open_chat的关闭逻辑。

_open_chat由标准库asynccontextmanager包装。yield把本次ChatService交给代码块使用；代码块结束后继续执行清理。聊天失败或取消时也尝试关闭，关闭再失败时保留原聊天异常并关联关闭异常。

ModelGateway.aclose关闭异步SDK客户端，再在线程中关闭同步客户端。成功取得的网关是本次请求使用的资源，不放进共享服务缓存。

## 11. 返回模型和响应头如何组成HTTP响应

你返回ChatReplyResponse(content=reply)。FastAPI根据response_model检查并序列化它，最终正文类似：

```json
{"content":"模型回复"}
```

response.headers设置Cache-Control:no-store和Pragma:no-cache。日志中间件再加入X-Request-ID，让用户看到的这次HTTP请求与服务端日志对应。这个日志ID和正文中用于请求去重的request_id职责不同。

## 12. 重试接口具体有什么不同

POST /sessions/{session_id}/retry不需要新的问题正文或请求ID。身份和服务依赖与发送相同，路由await service.retry_message(user_id=current_user.user_id, session_id=session_id)。

原ChatService查找本人的未完成问题，再领取处理权、读取最新上下文并尝试生成。不会调用start_turn，不另存“继续”。没有待回复问题时返回业务参数错误400。

实际验证中，发送模拟超时得到504，GET历史只看到原human消息；随后重试成功得到200，历史变成一条human和一条ai。

## 13. 异常在哪里转换

KNOWN_CHAT_ERRORS是异常类型元组。路由捕获其中的已知错误，交给_raise_chat_http_error记录安全日志并抛HTTPException；NoReturn只是一种类型标注，说明这个辅助函数不会正常返回。

| 原因 | 对客户端的结果 |
| --- | --- |
| 网站登录Token无效 | 身份依赖返回401 |
| 请求结构不合法 | FastAPI与安全校验处理器返回422 |
| 会话不存在或不属于当前用户 | 404 |
| 未配置个人Key | 400，提示先配置 |
| 供应商拒绝个人Key（401/403） | 400，提示检查个人模型配置 |
| 通用业务参数不合要求 | 400 |
| 数据库故障或密文无法解密 | 503，“请稍后重试。” |
| 模型限流 | 429 |
| 模型连接或其他已知SDK故障 | 502 |
| 模型超时 | 504 |
| 未预期异常 | 请求中间件返回通用500 |

网站登录Token和供应商API Key是两种凭证，所以两种401不能混为一谈。日志保留安全的位置和异常类别，不回传供应商原文、数据库细节、密码、Key或原始Token。

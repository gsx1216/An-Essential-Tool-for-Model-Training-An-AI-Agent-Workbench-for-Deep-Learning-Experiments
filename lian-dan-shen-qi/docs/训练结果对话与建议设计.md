# 训练结果对话与建议设计

确认日期：2026-10-25。

## 1. 已确认的用户目标与当前进度

训练结束后，用户能够围绕这一次训练继续聊天。聊天大模型应读取本次运行的指标、配置、相关日志和已保存的分析，结合用户问题解释训练表现，给出有依据的改进建议；不能只生成一份孤立报告。

负责对话分析的是用户配置的聊天大模型；训练产出的模型权重作为实验产物单独保存。如果以后还需要直接与训练得到的语言模型聊天，需另接模型推理服务，不属于本阶段已经具备的能力。

当前已实现实验登记、普通聊天和运行记录基础，以及 /runs/latest-training 本人最近训练查询接口，见 [实验运行记录与最近训练查询说明](实验运行记录与最近训练查询说明.md)。训练执行、指标采集、结果报告、run 与聊天会话的关联及模型工具调用仍未接通。现有 SendMessageRequest 仍只有 content 和 request_id，不支持直接传入 run_id；新增后端查询不等于模型已会调用它。

## 2. 必须打通的流程

```text
用户创建实验 → 提交一次运行 → 执行器训练并收集指标和日志
                                  ↓
                     保存运行状态、配置快照、结果与产物引用
                                  ↓
                     生成结构化结果报告，记录报告版本
                                  ↓
              用户从运行详情点击“讨论结果”，关联聊天会话与运行
                                  ↓
             校验归属 → 读取报告与相关证据 → 组装模型上下文
                                  ↓
                 大模型回答用户问题、给出建议与验证方法
                                  ↓
                  用户继续追问，或选择建议创建下一次运行
```

失败、中止和指标不全的运行也能讨论。必须明确区分“训练成功退出”“指标是否满足目标”“分析是否成功生成”，不能把进程退出码 0 自动解释为模型效果良好。

## 3. 各部分需要保存什么

| 部分 | 计划保存和负责的内容 |
| --- | --- |
| experiments | 已实现的实验定义：目的、类型、说明和归属 |
| experiment_runs | 已实现归属、定义/参数快照、状态元数据及引用预留；代码版本、真实日志和结果由执行阶段补齐 |
| 指标与产物 | step/epoch、训练和验证指标；完整日志和权重放文件或对象存储，数据库保留引用及必要索引 |
| 结果报告 | 最优值、末尾值、趋势、异常及缺失信息，关联具体 run_id 和报告版本；普通统计先由代码计算 |
| 分析与建议 | 关联运行和报告版本，记录证据、可能原因、建议改动、预期效果及验证方案 |
| 聊天关联 | 持久保存会话关联的运行以及当前讨论对象，支持服务重启后恢复；回答引用的运行/报告版本也应可追溯 |

上述后续数据结构需要在对应阶段具体设计，不能为了聊天简单地把完整训练日志重复写入 chat_messages。

## 4. 聊天如何知道本次结果

用户可以从运行详情发起讨论，也可以在全新聊天中询问“最近一次训练结果”。前者直接选择 run_id；后者先按当前身份查询运行，再关联具体 run_id。后续请求根据这个关联加载结果。不依赖大模型从一长段旧对话中猜测当前讨论的是哪次实验，也不只保存于某个 Python 对象的内存。

每次结果问答均校验聊天会话和运行都属于当前 Token 对应用户。浏览器提交运行 ID 只用于选择对象，不能作为授权证明。日志读取由后端根据受控引用完成，不接受任意文件路径。

准备模型输入时纳入：实验目标、选定运行的配置与结果报告、与问题相关的有界指标/日志、既有聊天摘要及最近对话、当前问题。所有新增结果材料也要纳入完整输入预算，复用已有上下文管理，不能额外无限追加日志。

日志与报告作为待分析数据传入，不作为更高权限的系统指令。指标缺失就标明缺失，不虚构结果或将“未观测到”写成“没有问题”。建议要区分事实、推断及需要验证的假设。

只有一个明确讨论对象时，“这次”“这个结果”沿用当前关联运行；比较运行 A 和 B 时加载两份结果。指代不明确时请用户选择，不盲猜。切换运行后重新取对应报告；重试一次失败回复时应保持原问题关联的运行和报告版本。

首次不需要 RAG 也能按 run_id 精确读取结果。日志或历史运行规模增长后，再评估按问题检索证据；检索不替代归属检查和明确的运行关联。

## 5. 对话与自动分析的关系

训练结束先持久化可读的结构化结果，不要求用户上传或手动粘贴日志。用户主动提问即可调用本人配置的模型 Key 分析；训练结束自动调用模型生成分析可作为用户选择启用的选项。

模型或 Key 暂不可用时，训练结果仍然保存，可查看报告并稍后继续分析。分析失败不能把已经成功结束的训练改成训练失败。

给出建议、应用修改、再次运行是不同操作。建议不能直接表示文件已经修改；实际应用后应记录 diff、原始运行与后续验证运行，沿用用户配置的自动运行/自动应用策略。

## 6. 后续实现顺序与验收条件

1. experiment_runs（基础已完成）：运行记录、定义/参数快照、用户归属及最近训练查询；尚未实际运行。
2. Runner 与采集：能得到真实的状态、日志、指标和产物。
3. 结构化结果报告：完整、缺失、失败运行都能正确展示。
4. 运行与聊天关联及结果问答：复用现有聊天、个人 Key、重试和上下文管理。
5. 自动分析/建议、下一次运行及修改追踪，之后接入任务队列和恢复机制。

“训练结果可以对话”完成前必须验证：

- 不手动粘贴结果，用户提问时仍会加载所选运行的真实数据。
- 全新会话没有旧聊天历史，也能按当前用户查询最近一次训练并读取报告。
- 持续追问、切换运行、比较两次运行都能保持明确对象。
- 另一用户即使知道 run_id 也不能读取、关联或讨论该运行。
- 重启服务后关联仍存在；失败回复重试不会悄悄切换结果版本。
- 缺少指标、训练失败、模型调用失败均有清楚状态，已保存的结果不丢失。
- 历史摘要后仍保留结果引用，长日志不会绕过模型输入预算。
- 单元和联调优先使用模拟训练、模拟模型与独立临时库，不自动产生付费调用。

本设计最初用于确认需求；运行记录基础已在后续阶段实现并验证。训练、报告与聊天工具仍按上述顺序接入，没有启动真实训练或收费模型。

## 7. 全新会话查询“最近一次训练结果”

这是一项明确需求：用户不必先打开旧聊天、选择运行详情或手动提供日志。新会话中的自然语言请求也能触发受控的数据查询。

```text
新聊天：“最近一次训练结果是什么样的？”
  → 校验 Token，取得当前 user_id
  → 识别需要查询训练运行，调用后端工具
  → 在当前用户、训练类型范围内查询最近提交的一次运行
  → 取得具体 run_id、运行时间、状态和结果版本
  → 读取结构化报告及必要日志片段
  → 关联当前聊天与本次运行，保存回答的数据来源
  → 大模型解释结果、回答问题并给出建议
```

工具能力计划拆分为：查询最近训练运行、获取某次运行报告、读取该运行的有界日志片段。模型只提出查询需求和参数；当前 user_id 由后端从认证结果注入，不能由模型或浏览器任意选择。工具每次读取都要核对运行归属，也不能接收任意服务器文件路径。

默认“最近一次”指当前用户最近提交的训练运行，按创建时间及稳定 ID 排序，不把其他用户、普通脚本运行或旧聊天中的偶然记录混入。用户指定某个实验时只在该实验范围内查找；说“最近一次已完成的训练”时显式按完成状态过滤。后续运行记录应提供支持这些查询的索引。

如果最近一次仍在训练，回复明确说明状态，只报告已采集的部分指标；如果失败则解释失败证据。如果要同时提供此前最近完成的一次结果，必须单独说明对应运行和时间，不能悄悄用旧结果代替最近运行。用户尚未运行过训练时，清楚说明没有可用记录。

回答应标明所讨论的实验、运行时间和状态。解析出具体 run_id 后，将关联与报告版本持久化，后续“这次为什么这样”“怎么改”继续围绕同一运行；用户再次明确问“最近一次”时重新查询，不永远复用旧关联。一次失败回答的重试保持原问题已选定的运行和版本。

查询以已保存的运行记录、指标和日志为来源，不要求复制所有旧聊天。第一版可以直接按用户、类型、时间和 run_id 查询，不依赖 RAG；大日志仅在需要时分段读取，并纳入完整输入预算。

增加验收：全新会话查询最新运行、没有训练记录、最新仍在运行、最新失败、指定实验范围、跨用户隔离、同时间戳排序、后续指代和重新查询最新运行，以及工具读取失败后的安全回复。后端最新查询及其范围、状态测试已完成；其余会话关联、日志报告和模型工具仍待接通。

## 8. 服务器和外部研究证据

用户明确要求 Agent 连接训练服务器、联网检索相似研究，并依证据提出修改建议。后续通过受控服务器工具读取运行事实，通过研究工具保存实际检索/读取的来源。每条建议关联 run_id、报告版本、指标/日志位置、论文或官方资料引用、适用条件及验证方案；不足的证据标为待验证，不伪造引用或将猜测写成结论。

这部分尚未实现，详见 [服务器连接与有据建议设计](服务器连接与有据建议设计.md)。该要求是后续功能验收条件，不能仅靠提示词声明“有依据”来替代真实工具和来源校验。


## 2026-10-26 更新：聊天只读训练工具已接入

普通聊天可直接回答；查询训练时，模型按需调用 get_latest_training_run、get_run_report、get_run_logs，后端使用真实登录身份校验本人范围。会话运行关联和工具审计保存在新增的 chat_run_bindings、chat_tool_calls 中，共 18 张业务表。工具不启动/停止任务，不同步指标或生成报告。

支持服务重建和历史摘要后的连续追问，查询循环/结果/超时有界，失败保留原问题可重试；删除会话级联清理关联和审计，不删除实验运行。详情见 [聊天只读训练工具与会话运行关联说明](聊天只读训练工具与会话运行关联说明.md)，完整文件清单见 [聊天只读工具阶段文件变更清单](聊天只读工具阶段文件变更清单.md)。下一步补真实模型验收、联网研究与引用依据，再扩展后台监控与任务协作。

## 3. 从入口按顺序看

### prepare(history, summary)

history 来自调用方读取的可信服务端消息列表，每一项是 ContextMessage(seq, role, content)，最后一项是本次待答的 human 问题。summary 是旧 ContextSummary，首次没有时为 None。

prepare 先调用 validate_history 检查对象、角色、顺序、正文与摘要范围；再计算系统提示词和当前问题占用。如果当前问题已经超出预算，调用已有 _prepare_long_input；否则进入 _prepare_history_context。

### _prepare_history_context(history, summary)

先用 _assemble_messages 把系统提示词、旧摘要、历史原文和缺口标记组装成模型所需的二元组列表，再用 _count_input 计算完整输入。

未达到 compact_at_tokens 时直接返回。达到阈值时调用 _split_for_summary，取得两个新列表：

- older：这次要总结的较早前缀。
- recent：保留的最近 keep_recent_turns 组原文，以及最后的当前问题。

默认保留最近 4 组。正常连续历史中，一组通常是 human + ai；有缺失时，一组也可能只有单条真实消息，不能补造另一条。

older 为空时没有新的较早原文可总结：完整输入仍在硬预算内则直接返回，超过硬预算才提示缩短材料或拆分任务，避免无意义调用模型。

### covered_until、covered_gaps 和 boundary

```python
covered_until = older[-1].seq
covered_gaps = tuple(
    gap for gap in missing_ranges
    if gap.end_seq <= covered_until
)
version = 1 if summary is None else summary.version + 1
```

covered_until 是最后一条被本次新摘要覆盖的真实消息序号，不是消息数量。

例如旧摘要覆盖 1～10，其中 2～3 缺失；本次 older 是 11、12、15、16，recent 是 19、20、21。那么新摘要覆盖到 16，带上 2～3、13～14 的缺口；17～18 的缺口仍属于近期原文，不写成新摘要已经覆盖了它。PreparedContext.missing_ranges 仍记录这三个范围。

boundary 是临时 ContextSummary，正文写“摘要待生成”，只给近期消息校验和预算计算提供覆盖边界。普通摘要分支不会把这句占位正文发给模型，也不会保存它。这样就不会把已准备总结的 older 误认为近期历史丢失。

如果系统提示词和必须保留的近期原文本身已超预算，先明确提示拆分，不浪费摘要调用。

### await summarizer.summarize(...)

```python
new_content = await self.summarizer.summarize(
    previous_summary=summary,
    messages=older,
    max_tokens=self.max_summary_tokens,
    missing_ranges=covered_gaps,
)
```

previous_summary 是上次摘要；messages 只包含较早前缀；max_tokens 是新摘要预算；missing_ranges 是新摘要所覆盖的未知信息范围。当前问题与保留的 recent 不交给历史摘要器。

这里的 summarizer 是构造 ContextManager 时传入的对象。测试传 FakeSummaryGenerator，真实适配器是新增的 ModelHistorySummarizer。Protocol 只规定方法长什么样，不会自动创建或调用模型。

### 校验、创建新摘要、返回

摘要必须为非空白字符串，而且自身计数不能超过 max_summary_tokens。strip 只用于判断空白，不会用去掉空格后的文本替换摘要。

验证通过后，新建 ContextSummary(new_content, covered_until, version, covered_gaps)，再组装“系统提示词 + 新摘要 + recent + 缺口标记”，对完整结果重计数。

超过输入硬预算时提示拆分；没有减少总占用时抛 ContextCompactionError，避免把更长的结果作为成功摘要。所有校验都通过才返回 PreparedContext。

过程中没有给传入的 summary 重新赋字段，也没有删除 history 的元素。失败或取消时，原摘要和原文仍由调用方保留。

## 4. 新增的真实历史摘要器怎样工作

app/services/history_summarizer.py 中的 ModelHistorySummarizer 实现同一个 summarize 方法：

1. 检查摘要、消息、预算和缺口元组；缺口说明必须与原文真实缺口一致。
2. 将已有摘要、新增原文片段和缺口说明编码为 JSON 历史资料。每个原文片段带真实 seq、role、正文和字符范围，资料内容不提升为 system 指令。
3. 对包含提示词和 JSON 的完整摘要请求计数。能放下时合并消息为一批；单条也太长时切开正文，按 start_char、end_char 标明片段位置，保留所有字符，不截掉尾部。
4. await gateway.invoke(request, max_tokens=output_limit) 等待摘要模型。输出额度会给消息格式开销留空间，之后仍检查真实返回结果。
5. 本批摘要作为下一批的已有摘要，继续合并，直到所有 older 被覆盖才返回最终文本。

默认摘要请求输入预算 12000、最多 16 次网关逻辑调用、整体等待 180 秒。底层 SDK 自身已有重试，逻辑调用数不等于 HTTP 尝试数。超限会明确失败，不把处理了一半的摘要冒充完整结果。

超时和供应商异常转为固定 ContextCompactionError 说明，项目日志保留安全异常分类；主动取消继续抛出 CancelledError。

这个适配器只接收调用方传来的网关，不读取全局 Key，不查询数据库，也不负责关闭调用方仍要用于回答的网关。正式接入时，网关必须属于当前已登录用户。

## 5. 长问题与长历史怎样一起处理

原文很长时，_prepare_long_input 仍然先保留原文，只对工作副本生成问题精简稿。

若旧历史已占满预算，会按计划保留的 recent 和摘要额度预留问题空间。问题精简后完整输入仍过长、且存在可总结的 older，就调用同一个 _prepare_history_context 继续做历史摘要。

因此两个标志可能同时为 True：

| input_compressed | was_compacted | 含义 |
| --- | --- | --- |
| False | False | 直接使用当前问题和现有历史 |
| True | False | 当前问题使用精简稿，历史未生成新摘要 |
| False | True | 当前问题保留原文，旧历史生成新摘要 |
| True | True | 当前问题精简后，又为旧历史生成新摘要 |

如果近期原文本身过大，或者最终结果仍然超限，仍需拆分任务。自动摘要不保证任何长度都能放进固定窗口，模型摘要也不保证完全无损；原文保留供以后回查。

## 6. 各文件与导入对象的职责

| 文件或导入 | 来源 | 当前作用 |
| --- | --- | --- |
| context_manager.py | 本项目 | 决定何时精简、总结哪些历史、保留哪些原文、校验并返回完整输入 |
| history_summarizer.py | 本项目 | 把旧摘要与较早原文分批交给模型合并 |
| input_compressor.py | 本项目 | 精简当前问题，与历史摘要分工不同 |
| context_contracts.py 中的 Protocol | typing，Python 标准库 | 规定计数器和两个生成器的方法接口，便于替换成真实或测试对象 |
| ContextMessage / ContextSummary / HistoryGap / PreparedContext | 本项目，使用标准库 dataclasses | 传递消息、摘要、缺口和准备结果，不自动写数据库 |
| asyncio | Python 标准库 | await 期间允许其他任务执行；timeout 限制摘要整体等待时间 |
| json.dumps | Python 标准库 | 将历史片段编码成 JSON 字符串，不是 SQL 注入或数据库写入 |
| ModelGateway | 本项目，内部使用第三方 langchain_deepseek | 发起异步模型调用并统一返回 content、usage |
| logged_operation / logging_context | 本项目 | 持久记录位置、耗时、结果和固定异常分类，不记录正文、Key 或 Token |
| unittest / AsyncMock / deepcopy | Python 标准库 | 模拟依赖、检查分支、验证原始输入没有被改变 |

计数、列表切分和创建数据对象都是同步操作，不写 await。摘要器和模型网关是异步方法，需要 await。这里没有数据库操作，所以不需要 asyncio.to_thread；以后读取和保存 MySQL 时仍由对应服务按已有方式处理。

# 聊天业务异常与日志说明

本次把三种已知业务拒绝从普通 `ValueError` 分离出来，让用户知道如何操作，让日志能够直接说明原因。没有修改数据库结构、个人 Key、模型配置或聊天状态机。

## 1. 接口会返回什么

| 操作 | 状态码 | 响应中的 detail |
| --- | --- | --- |
| 同一会话中，用旧 request_id 提交不同的问题 | 409 | 该请求编号已用于其他问题，请为新问题生成新的 request_id。 |
| 会话还有未完成问题，却用新 request_id 提交新问题 | 409 | 当前会话还有未完成的问题，请先重试或新建聊天。 |
| 会话没有未完成问题，却调用 retry | 400 | 当前会话没有等待回复的问题。 |

409 表示当前请求与服务端已有的业务状态冲突；400 表示当前没有可执行的重试操作。这三种情况属于预期的操作拒绝，日志级别是 WARNING。

普通参数校验仍然返回通用 400。数据库或密文解密故障仍返回 503 和“请稍后重试。”；供应商错误继续使用现有的安全提示。本次没有把任意异常的原始文字直接回传给用户。

## 2. 各文件负责什么

| 文件 | 职责 |
| --- | --- |
| app/errors.py | 定义 RequestIdConflictError、UnfinishedTurnError、NoPendingReplyError，表示三种不同业务原因。 |
| app/repositories/message_repository.py | start_turn 在数据库事务中检查已有轮次和消息；发现请求编号冲突或未完成问题时，抛出对应异常并回滚。 |
| app/services/chat_service.py | retry_message 查询未完成轮次；结果为空时抛出 NoPendingReplyError，不调用模型。 |
| app/api/chat_routes.py | 把具体业务异常转换为固定 HTTP 状态码和提示，并在 OpenAPI 文档中声明 409。 |
| app/logging_config.py | 将异常类型映射为安全、明确的日志原因，复用已有的文件日志、代码定位和异常去重。 |

## 3. 从请求到日志的实际顺序

### 发送新问题

1. FastAPI 校验请求体，并通过 require_current_user 确认登录身份。user_id 来自登录 Token 的校验结果，不能通过请求体指定其他用户。
2. 路由调用 UserChatService.send_message，传入当前用户、会话 ID、问题内容、请求编号。
3. UserChatService 为当前用户读取并解密个人 Key，创建本次请求使用的模型网关，再调用 ChatService。
4. ChatService 使用 `await asyncio.to_thread(...)` 调用同步的 MessageRepository.start_turn。
5. 仓储锁定并检查会话归属，然后查询当前请求编号是否已经存在。
6. 已存在且内容不同：抛出 RequestIdConflictError；已存在且内容相同：复用原轮次，仍保留原来的防重复行为。
7. 请求编号是新的，但还有未完成问题：抛出 UnfinishedTurnError。
8. 上述异常发生时，事务回滚，不追加消息，不发起模型生成。网关对象可能已经创建，但会在退出时关闭。
9. 异常向上传递，路由将它转换为固定的 HTTP 409 响应。

### 重试问题

1. 登录身份和会话归属按原有流程校验。
2. ChatService.retry_message 查询当前会话的未完成轮次。
3. 如果没有结果，抛出 NoPendingReplyError，路由返回明确的 HTTP 400。
4. 如果有结果，继续现有的领取任务、重新读取上下文、生成和保存回复流程，不额外插入一条用户问题。

## 4. 为什么不能继续全部抛 ValueError

普通 ValueError 只能说明“某种值或状态不符合要求”，接口无法仅根据这个类型判断具体原因。新的异常类继承 ValueError，因此既保留现有捕获、日志和回滚行为，又能让接口识别具体类型。

路由必须先判断三种具体异常，再判断普通 ValueError。否则子类会先匹配通用分支，再次变成“请求参数不符合要求。”

不要通过比较 `str(error)` 来决定响应，也不要直接 `detail=str(error)`。本次根据异常类型选择固定提示，错误对象即使意外携带敏感信息，也不会被原样返回或写入日志。

## 5. 日志如何记录

| 异常类型 | 原因分类 |
| --- | --- |
| RequestIdConflictError | 同一请求编号被用于不同问题 |
| UnfinishedTurnError | 会话存在尚未完成的提问 |
| NoPendingReplyError | 会话没有等待回复的提问 |

现有 `@logged_operation(...)` 在仓储或服务抛出异常时记录一次 WARNING。日志保留操作名、实际抛出位置、线程、异常类型和服务端请求编号；各层继续抛出同一个异常时，已有的上下文记录会防止重复写入同一异常。请求结束时还会单独记录 HTTP 状态和总耗时，这是请求结果记录，不是重复的异常明细。

日志中的 request_id 对应响应头 X-Request-ID，用于串联一次 HTTP 请求。请求体中的 request_id 用来识别一个逻辑问题，两者用途不同。

不记录问题原文、API Key、密码、原始 Token、密文、SQL 参数或任意异常正文。默认日志仍按日期写入 logs 目录。

## 6. 相关导入和工具

- Python 内置的 ValueError：三种业务异常的父类，不需要安装包。
- 项目自己的 app.errors：仓储、服务和接口共享异常定义；它不依赖 FastAPI，业务层无需了解 HTTP。
- 标准库 asyncio.to_thread：将现有同步仓储调用放到工作线程，await 等待结果；仓储异常会回到异步调用方。
- 第三方 FastAPI 的 HTTPException：仅在接口层表达 HTTP 状态码和响应内容。
- 标准库 logging：使用 WARNING 记录预期拒绝。
- 项目自己的 logged_operation 和 log_failure：处理持久化、安全原因分类、源码定位和异常去重。无需为每个 raise 再手写一份日志。

## 8. 手动验证建议

启动 `python -m scripts.run_chat_api_demo`，在 8001 端口使用临时账号和假 Key 验证即可，不需要为错误分支测试请求真实收费模型。

发送一个问题成功后，在同一会话中保持原 request_id、修改内容，应返回 409。模型模拟超时留下未完成问题后，用新 request_id 发新问题，应返回另一个 409；重试原问题成功后再点 retry，应返回明确的 400。

使用 `--simulate-timeout` 启动演示时，请按先注册、登录、配置假 Key、创建会话、首次发送的顺序操作，模拟首次发送超时后再测试相关拒绝和重试。

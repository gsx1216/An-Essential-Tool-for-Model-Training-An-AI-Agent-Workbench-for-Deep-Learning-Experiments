## 3. 输入不是普通的二元组列表

之前 ModelGateway 使用：

```python
("human", "问题")
```

但摘要必须记住它覆盖到了哪里，所以内部历史还要保留真实消息序号：

```python
from app.models.context_state import ContextMessage

history = [
    ContextMessage(seq=1, role="human", content="学习率如何设置？"),
    ContextMessage(seq=2, role="ai", content="可以先测试较小的学习率。"),
    ContextMessage(seq=3, role="human", content="这个参数有什么影响？"),
]
```

- history[0].seq 是数据库消息序号，不是列表索引。
- history[0].role 是消息角色。
- history[0].content 是正文。
- history[-1] 是当前已经保存、等待回复的用户问题，不能重复添加。

后面接入仓储时，SQL 会返回真实 seq；不能用 enumerate 临时编号来冒充数据库序号。接口显示历史与模型上下文读取仍然分开。

## 4. 摘要如何表达

```python
from app.models.context_state import ContextSummary

summary = ContextSummary(
    content="已确认训练目标和学习率调整方案。",
    summarized_until_seq=10,
    version=3,
)
```

这表示：第 3 版摘要已覆盖消息 1～10，后面的 history 预期从 seq=11 开始。history 中不能再把 1～10 重复放入。如果从 seq=13 开始，可以继续处理，但需标记 11～12 在本次上下文中不可用；不把这两条内容编造出来。

没有摘要时传 None，预期从 seq=1 开始；如果从更大序号开始，则标记前面的缺失范围。这是当前内部数据合同，不是让用户自己提交摘要或消息序号。

每次产生新摘要：

- summarized_until_seq 等于本次总结的最后一条原文的真实 seq。
- version 没有旧摘要时为 1，否则旧版本加 1。
- 当前问题始终处于摘要覆盖范围之外。
- missing_ranges 保留该摘要实际覆盖的缺口，例如 (HistoryGap(3, 4),)。生成摘要不会恢复未知的原文，也不能抹掉其不完整状态。

version 为后续条件写回、防止旧摘要覆盖新摘要提供依据。本轮暂不写数据库；真正接入时，还要校验用户身份、会话存在性、轮次 attempt_id 和摘要版本。删除的会话不能被迟到的摘要任务恢复。

本步骤先完成覆盖序号。结构化事实与逐条 source_seqs 引用将在摘要服务与历史检索阶段增加，并校验引用确实属于原文范围。

## 5. TODO 1 的校验顺序

建议先检查外层类型，再访问里面的属性，避免错误输入触发 AttributeError。

1. history 是非空 list。
2. summary 是 None 或 ContextSummary；摘要正文非空白，覆盖序号和版本为正整数，不能把 bool 当作整数。
3. 每个 history 元素是 ContextMessage。
4. 消息 seq 为正整数，严格递增，不能重复、倒序或与摘要覆盖范围重叠。允许向前缺号，缺失范围由 find_history_gaps 提取。
5. 连续片段内角色按 human、ai 交替；跨缺口时无法确定丢失角色，不强行沿用之前的交替关系。末尾仍必须是 human，代表当前真实存在的待答问题。
6. content 为非空白字符串；检查时可以用 strip 判断，不能替换原文，避免破坏代码缩进。

expected_seq 用来发现缺口或重复倒序，expected_role 用来检查连续片段。处理一条消息后，expected_seq 更新为它的真实 seq + 1，而不是给它重新编号。此方法不删消息、计数、调用摘要器或返回模型输入。

校验成功返回 None；校验失败抛 ValueError。dataclass 和 Literal 的类型注解不会自动替你执行这些运行时校验。

## 8. TODO 4～6：异步协调

prepare 的流程：

```text
校验输入
  ↓
检查系统提示词和当前问题的最低开销
  ↓
组装并计数
  ├─ 未达到阈值：返回未压缩结果
  └─ 达到阈值：
        选择 older 和 recent
        检查是否有可总结的旧轮次
        await 摘要器生成摘要
        检查摘要正文及其预算
        创建新摘要对象
        用新摘要和 recent 组装并重新计数
        返回压缩结果
```

摘要调用的参数已经写在源码注释里。previous_summary 是旧摘要对象，messages 是新增待总结原文，不包含当前问题；max_tokens 是摘要生成预算。

“达到触发阈值”不等于“超过硬预算”。只有当前问题、没有可总结历史时，如果仍低于硬预算，就正常返回。不能为了降低占用而把当前问题拿去总结。

无效摘要抛 ContextCompactionError；必要内容超过硬预算抛 ContextTooLargeError。摘要器本身失败则让原异常向上传递，保留旧对象；不清空历史、不把异常内容当成摘要，也不无限重试。

本练习每次 prepare 最多调用摘要器一次。后续 SummaryService 会负责摘要输入预算、分批总结和调用上限，再接入真正的模型。当前模块的 max_summary_tokens 不是全部输入上限。

## 9. prepare 返回什么

PreparedContext 包含：

- model_messages：本次实际交给模型网关的列表。
- summary：沿用的旧摘要，或本次生成的新摘要。
- input_tokens：使用注入计数器得到的输入计数。
- was_compacted：本次是否成功生成了新摘要。
- missing_ranges：旧摘要与本次原文的所有已知缺口，供后续日志和展示识别“不完整上下文”。

它不会直接修改 Redis 或 MySQL。调用方以后在确认摘要版本、会话和轮次仍有效后持久化，再使用准备好的消息请求模型。

dataclass(frozen=True) 禁止直接给字段重新赋值，但不是递归冻结；列表内部仍然可变。所以实现里必须新建列表，不能依赖 frozen 自动保护 history。

## 10. 计数器和摘要器为什么分开

TokenCounter 和 SummaryGenerator 是标准库 typing.Protocol 描述的方法合同，不是实际计数或模型实现，也不是额外的模型服务。

- self.counter.count_messages(...)：同步计数，返回整数。
- await self.summarizer.summarize(...)：异步生成摘要，返回正文。

练习脚本传入 FakeTokenCounter 和 FakeSummaryGenerator。假计数器使用字符长度加固定开销作为测试刻度，便于稳定触发分支；它不是 DeepSeek tokenizer，绝不能用于正式预算判断。

真正接入前要确定计数方式及余量，并满足“输入 + 输出预留 + 安全余量”不超过供应商上限。系统提示词、摘要标记、消息格式、后续工具定义与检索结果都要算进去；实际 usage 用于校准。

## 这次的数据是什么

返回值是元组列表，每条消息包含三个值：

```python
[
    (1, "human", "你好"),
    (2, "ai", "你好，有什么需要帮助？"),
]
```

seq 是数据库保存的消息顺序，role 是角色，content 是消息内容。读取时不重新编号，也不新建 UUID 或写入消息。

旧的 MessageRepository.load_messages 为 ChatService 提供 (role, content) 历史，保持原有行为。新方法 load_history_page 为界面提供带 seq 的分页历史，分页结束位置来自数据库真实序号。

## 分页怎样使用

参数默认值：after_seq=0、limit=50。after_seq 允许从0开始的整数，limit 为1～100；仓储会拒绝布尔值、错误类型及越界数值。

例如已有四条消息，每页两条：

| 读取 | 参数 | 返回序号 |
| --- | --- | --- |
| 第一页 | after_seq=0，limit=2 | 1、2 |
| 第二页 | after_seq=2，limit=2 | 3、4 |
| 继续读取 | after_seq=4，limit=2 | 空列表 |

after_seq 表示“已经读到哪条消息”，下一页从大于它的序号开始。它不表示用户 ID 或页数。用户打开会话时从0开始读取，后续使用上一批最后一条消息的 seq。

每页少于 limit 条表示已读到当前末尾；恰好等于 limit 时，还可以请求下一页确认。暂不提供 has_more 字段。

## 调用逻辑与权限

```text
未来 GET /sessions/{session_id}/messages
  → Token 确认当前用户
  → ChatHistoryService 校验参数、调度工作线程
  → MessageRepository 检查会话归属
  → SQL 按 seq 排序并限制数量
  → 返回一页历史
```

服务接收 user_id，未来由路由使用 current_user.user_id 传入。normalize_session_id 检查 UUID 格式，实际会话是否属于该用户由仓储检查。

有效且没有消息的会话返回 []。会话不存在、已删除或属于别人时抛出 SessionNotFoundError；未来接口统一返回404。不能把“无权读取”和“有效的空聊天”当成同一种成功响应。

仓储原有的会话缺失异常已明确为 SessionNotFoundError，它继承 ValueError，因此原先捕获 ValueError 的调用仍兼容。参数不合法继续抛 ValueError，数据库故障继续向上传播；未来路由分别处理400和通用503。

不要捕获数据库异常后返回 []，否则前端会把故障当成聊天记录为空。
